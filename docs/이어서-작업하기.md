## 2. 스테이지 만드는 법 (핵심 작업 흐름)

1. 디버그 빌드 실행 → 홈 우상단 공구 아이콘 → 에디터
2. 프리셋 모드에서 지형(platform: w·angle 조절)·목표물(basket/button)·미리 놓을
   동적 부품 배치, 목표 타입·world/index 지정
3. 부품 모드에서 정답 장치를 직접 배치 → ▶로 실제 클리어되는지 시험
4. **[Record Solution]** — 현재 배치가 solution으로 저장된다
5. **[Export]** — JSON이 클립보드에 복사됨 → `assets/stages/w{월드}_s{번호2자리}.json`
   으로 저장 (예: `w1_s04.json`)
6. `lib/sim/registry.dart`의 `stageOrder`에 id 추가 — **이 순서가 곧 해금 순서다**
7. 검증 도구(아래 3절)를 돌려 통과 확인 후 커밋

스테이지 JSON 스키마 (파서: `lib/sim/stage_data.dart`, 실패 시 스테이지 id가
포함된 FormatException):

```json
{
  "id": "w1_s01", "world": 1, "index": 1,
  "goal": { "type": "ball_in_basket" },
  "preset": [
    { "type": "platform", "x": 8.0, "y": 7.2, "angle": 0, "w": 15.5 },
    { "type": "basket", "x": 13.0, "y": 6.7, "angle": 0 },
    { "type": "rubber_ball", "x": 1.5, "y": 1.0, "angle": 0 }
  ],
  "tray": [ { "type": "plank", "count": 1 } ],
  "solution": [ { "type": "plank", "x": 11.0, "y": 6.0, "angle": -20 } ]
}
```

- 좌표: 미터, y 아래로 증가, 원점 좌상단, 월드 16×9m. 각도: 도(시계+)
- 플레이어 배치 가능 영역은 중심 기준 x 0.3~15.7, y 0.3~7.3 (프리셋은 제한 없음)
- 목표 4종: `ball_in_basket` `press_button` `pop_balloons` `topple_dominoes`
  — 풍선·도미노 목표는 **프리셋으로 놓인 것만** 카운트한다(플레이어가 추가로
  배치한 풍선은 총계에 안 들어감)

## 3. 검증 도구

`tool/validate_stages.dart` + `lib/sim/validate_core.dart`(도구·테스트 공용, 순수 Dart):

1. `assets/stages/*.json` 전부 파싱 + `registry.stageOrder`와 파일 목록 1:1 대조
2. 각 스테이지의 solution을 `SimWorld.verify(stage, solution, maxSteps: 1800)`로
   실행 → 클리어돼야 통과
3. **지터 강건성**: solution 좌표에 x±0.05m, 각도±2°를 준 변형 3종도 전부
   클리어돼야 통과 — 손가락 배치 오차에도 풀리는 정답만 허용하기 위해서다
4. **배치 합법성(rule e)**: solution을 저자가 적은 순서 그대로 하나씩
   `lib/sim/placement_rules.dart`의 canPlaceAt/snapGearPosition에 통과시켜
   본다 — 프리셋 + 그 앞에 놓인 solution 파트들과 안 겹치고 화면 안(x
   0.3~15.7, y 0.3~7.3)에 있어야 하며, 톱니류는 이미 스냅된 위치에 저장돼
   있어야 한다. 그리고 solution이 쓰는 부품 개수가 tray를 넘지 않아야 한다.
   **물리로는 클리어되는데 게임 자신의 배치 규칙으로는 플레이어가 못 놓는
   정답**을 걸러내기 위해서다 — 40판을 처음 다 만들었을 때 14판이 실제로
   이 문제였다(80°+ 근수직 판자·회전된 플랫폼의 conservative AABB가 실제
   폭보다 훨씬 커서 프리셋을 감싸거나, 좌표가 화면 경계를 살짝 벗어나는
   식). 물리보다 먼저 돈다 — 놓을 수조차 없는 정답을 1800스텝 돌릴 이유가
   없고, 더 근본적인 문제이기도 하다
5. 실패 시 exit 1 + 스테이지별 표(클리어까지 걸린 스텝 수) 출력
6. 같은 검사를 `test/stages_validate_test.dart`로도 감싼다(프로젝트 루트에서
   `dart:io`로 파일을 직접 읽으면 rootBundle 없이 된다)

에디터의 Export 버튼(`EditorState.exportJson`)도 4번과 같은 배치 합법성
검사를 통과 못 하면 거부한다 — 검증 도구를 돌리기 전에 애초에 못 놓는
정답을 못 내보내게 막는 2중 방어.

시뮬레이션이 계속 실패하면 **에디터로 열어 실제 거동을 보고 스테이지 좌표를
고친다.** `lib/sim/catalog.dart`의 물리 상수를 테스트 통과용으로 건드리는 것은
금지 — 상수를 바꾸면 이미 만든 모든 스테이지의 거동이 함께 변한다.

## 4. 스테이지 40판 구성안 (완성 — 아래는 제작 당시의 설계 초안)

월드마다 새 부품을 도입하고 이전 부품과 조합한다. 첫 3판이 튜토리얼 역할
(부품 1~2개, 배치가 자명). 아래는 설계 당시의 컨셉 초안이고, 실제 구현은
스테이지별로 조금씩 달라졌다(예: w1_s09/s10은 "갈림길"이 아니라 "널빤지로
플랫폼 틈 잇기"로 구현됨 — 이런 차이는 정상이다, 컨셉 초안일 뿐이었으므로).

## 5. 효과음 (완성)

- `tool/gen_sfx.dart`(순수 Dart)로 짧은 wav 7종 합성: tap(1kHz 30ms) ·
  place(500→300Hz 80ms) · pop(노이즈 60ms) · boing(150Hz 진동 200ms) ·
  win(도미솔도 아르페지오 600ms) · gearTick(900Hz 20ms) · buttonClick(700Hz 40ms)
  → `assets/audio/`. 기계음이라 합성으로 충분하고, 아쉬운 것만 나중에 CC0로 교체
- `lib/services/sound.dart`: audioplayers AudioPool 캐시. **규칙 두 가지**
  (가족 앱에서 앱이 통째로 죽었던 원인): ① 풀을 새로 만들면 쓰던 풀은 반드시
  `dispose` ② 초기화·재생 실패는 삼켜서 무음 진행(소리 때문에 게임이 죽으면 안 됨).
  파일이 없으면 조용히 건너뛴다(에셋 매니페스트 확인)
- 트리거: 배치=place, 삭제=tap, 풍선=pop, 트램펄린=boing, 버튼=buttonClick,
  클리어=win, 톱니 회전 중 주기적 gearTick. 설정의 소리 스위치와 연동
- BGM은 파일이 있으면 루프, 없으면 무음(합성 BGM은 품질이 안 나온다 — 외부 곡으로)

## 6. 릴리스 준비

1. 서명: **완료** — `upload.jks`+`keystore.properties`가 `android/`에 있고(같은
   키를 전 앱이 공유), build.gradle.kts의 signingConfig가 연결돼 있다. 키가
   없으면 서명 없이 빌드되도록 짜여 있다(release 서명이 debug 키로 몰래
   바뀌는 사고 방지 — build.gradle.kts의 `hasReleaseKey` 분기 참고). 두 파일은
   `.gitignore` 처리돼 있어 `git status`에 안 보임. 키 백업:
   `C:\workAndroid\_서명키_백업\`
2. 버전 `1.0.0+1`. versionCode(+뒤)는 올릴 때마다 증가
3. 매니페스트 확인됨: 권한 **0개**(release 기준 — debug의 INTERNET은 도구용이라
   릴리스에서 자동 제거됨), 가로 고정, 에디터가 릴리스에 없음(kDebugMode 게이트)
4. `flutter build apk --release` → `apksigner verify --print-certs`로 서명 지문이
   기존 앱과 같은지 확인. AAB는 스토어에 올릴 때만
5. 스토어 문구 규칙: **광고·인앱결제·무료 이야기를 쓰지 않는다**(추후 계획과
   충돌— 지금 참인 문장을 미래의 거짓말로 만들지 않기). "과학상자"라는 단어도
   금지(국내 교구 상표). 단 데이터 보안 설문·콘텐츠 등급은 신고 사항이므로
   현재 빌드 그대로(수집 0) 정직하게 적는다
6. allowBackup은 기본값 유지(복원되는 게 클리어 기록뿐이라 사용자 이득)

## 7. 이 저장소의 함정 목록 (전부 실측)

| 함정 | 내용 |
|---|---|
| forge2d 버전 | **0.14.2+1에서 올리지 말 것.** 0.15부터 네이티브 C 바인딩이라 순수 Dart 검증 파이프라인이 무너진다 |
| `lib/sim/` 순수성 | Flutter/dart:ui import 금지. 색도 int로 저장하고 게임 계층에서 Color로 변환 |
| 물리 상수 | `catalog.dart`가 유일 출처. 테스트는 절대값이 아니라 행동 대비를 검증(스테이지가 안 풀리면 스테이지 좌표를 고친다) |
| setAsBox | half-extents를 받는다 — 상수표는 전체 크기라 반으로 나눠 조립 |
| 톱니 | 마찰 전달은 물리적으로 불가(핀 고정 원끼리 수직항력 0) — GearJoint 방식 유지. 감지 반경 r1+r2+0.05, 배치 스냅 r1+r2−0.03 |
| 배치 합법성 vs 물리 클리어 | 스테이지 solution이 물리로는 클리어돼도 게임 자신의 canPlaceAt(회전 AABB·경계)으로는 못 놓일 수 있다 — 특히 80°+ 근수직 판자·회전된 넓은 플랫폼은 conservative AABB가 실제 폭보다 훨씬 크다(3절 rule (e) 참고). 저작 시 에디터로 실제로 드래그해서 확인할 것, 손으로 좌표만 적지 말 것 |
| 지터는 트램펄린·바구니 각도도 흔든다 | validate_core.dart의 지터는 solution의 모든 placement에 각도±2°를 똑같이 준다 — 회전 불가능한 부품(트램펄린 등)도 예외가 아니다. 순수 수직 낙하 후 트램펄린이 살짝(2°) 기울면 그 자체로 좌우 방향이 갈린다 — "허공에서 빠르게 나는 공을 트램펄린 1개로 정확히 받아 정확한 방향으로 튕겨내기" 설계는 이 각도 지터 하나로 거의 항상 깨진다(w4_s08에서 실측 — 패들로 쳐서 날린 공을 트램펄린+선풍기로 유도하는 원안을 수십 번 재배치해도 지터를 못 넘겨서, 결국 패들은 모터 톱니와 맞물리기만 하는 장식으로 남기고 공은 순수 수직 낙하 후 트램펄린으로 받는 형태로 다시 짰다). 가로속도 0으로 만들고, 받는 바구니를 트램펄린 바로 위/근처에 두는 설계가 훨씬 안정적이다 |
| basket는 방향이 있다 | basket 프리셋의 바닥판·벽은 "위에서 떨어지는 공"을 전제로 배치돼 있다 — 공이 아래에서 위로 솟아오르며 들어가야 하는 배치라면 `angle: 180`으로 뒤집어야 한다(안 뒤집으면 센서 앞의 바닥판에 막혀 절대 안 들어간다 — w2_s06·w4_s08 참고) |
| Flame 드래그 좌표 | `DragUpdateEvent.canvasEndPosition`은 델타 이중계산 버그 — 시작 위치+`canvasDelta` 누적 방식 유지 (hud.dart·input.dart 주석 참고) |
