# 삐약과학 개발일지

시간 순서대로, 각 차수에서 만든 것과 **실제로 밟은 문제**를 남긴다.
같은 데를 다시 밟지 않기 위한 기록이므로 성공담보다 실패담이 자세하다.

## 1차 — 데이터 모델과 물리 코어

**첫 결정: 물리를 Flutter에서 완전히 떼어냈다.** `lib/sim/`은 Flutter를 import하지
않는 순수 Dart로 두고, 부품 조립·고정 타임스텝·목표 판정을 전부 여기 넣었다.
화면 없이 시뮬레이션을 돌릴 수 있어야 "전 스테이지 자동 검증"이 성립하기 때문이다.
(삐약푸쉬에서 `lib/engine/` 분리가 준 이득 — 솔버·검증 도구를 CLI로 돌린 것 — 을
그대로 계승한 구조다.)

**forge2d 0.15는 쓸 수 없었다.** 의존성을 추가하자 최신 0.15.0이 잡혔는데, 알고
보니 이 버전부터 순수 Dart 엔진을 버리고 **네이티브 Box2D v3 C 바인딩**으로
전환됐다(MSVC 필요, `dart run` 도구 불가). 순수 Dart 마지막 버전인 **0.14.2+1로
핀 고정**했다. 업그레이드하면 검증 파이프라인 전체가 무너지므로 이 핀은 의도된
것이다 — 캐럿(^) 없이 정확한 버전으로 박아 뒀다.

**좌표계는 처음부터 하나로 통일했다.** 미터 단위, **y 아래로 증가**, 원점 좌상단,
월드 16×9m, 중력 (0, 10). 화면 좌표와 방향이 같아서 렌더에서 축 뒤집기가 아예
없다. Box2D의 `setAsBox`가 **반폭·반높이(half-extents)** 를 받는 것만 주의하면
된다(부품 상수표는 전체 크기로 적혀 있어서 조립할 때 반으로 나눈다).

**시소가 무한 회전했다.** 중심 핀(revolute joint)만 달면 한쪽에 공이 얹힌 순간
계속 가속해 9.9라디안까지 돌며 공을 다 튕겨냈다. 실제 시소는 땅에 닿아 멈춘다는
점을 반영해 회전 제한(±0.6rad)을 걸었다. 이런 관절 상수도 부품 상수표(catalog)로
승격해 한 곳에서 튜닝한다.

**"통과하는 테스트"가 거짓말을 한 사건.** 풍선이 압정에 닿으면 터지는지 검사하는
테스트가 첫 판에 통과했는데, 뜯어 보니 풍선이 **화면 밖으로 떠올라 경계 정리에
지워진 것**을 "터졌다"로 오인한 것이었다. 마지막 y좌표가 압정 근처 범위(1.5~3.2m)
안이어야 통과하도록 조여서, "압정에서 펑"과 "화면 밖으로 실종"을 구분하게 했다.
이후로도 새 판정 로직마다 **일부러 조건을 뒤집어 테스트가 실제로 실패하는지**
확인하는 것을 규칙으로 삼았다.

## 2차 — 동력 부품: 톱니가 안 돌았다

톱니 전달의 첫 설계는 "마찰 전달"이었다 — 톱니를 마찰 높은 원으로 만들고 살짝
겹치게 놓으면 모터 톱니의 회전이 접촉면 마찰로 옆 톱니에 전달되리라는 것.
현실의 마찰차가 그렇게 돈다.

**결과: 0.0 rad/s. 얼마나 겹쳐도(0.03m든 0.2m든) 정확히 0이었다.** 원인은 튜닝이
아니라 물리였다. 마찰력의 상한은 `마찰계수 × 수직항력`인데, **둘 다 중심이 핀으로
고정된 원끼리는 서로를 누르는 힘이 생길 수 없다** — 겹침은 위치 보정으로만 처리되고
속도 수준의 수직 임펄스는 0에 머문다. 실제 마찰차가 도는 건 스프링이나 하중이
두 바퀴를 눌러주기 때문이고, 우리 장면엔 그런 게 없다.

그래서 **GearJoint로 전환**했다. 조립 시 톱니 가족(모터/일반/노)끼리 중심거리
≤ r1+r2+0.05면 맞물림으로 감지해 두 revolute 관절을 GearJoint로 묶는다. 외접
기어는 반대로 돌아야 하므로 비율 부호를 라이브러리 소스의 제약식에서 직접
유도했다(ratio = rB/rA). 결과는 정확히 반대 부호, 2.5/−2.5 rad/s로 잠긴다.
배치 시에는 근처 톱니에 중심거리 r1+r2−0.03으로 **스냅**시켜 감지 반경 안에
확실히 들어가게 했다.

**선풍기는 특수 케이스를 안 만들었다.** 바람 존 안의 모든 동적 물체에 같은 힘
1.5N을 준다. 고무공은 밀리고 쇠공은 거의 안 밀리는 건 질량 차이가 만들는 자연스러운
결과다(a = F/m). "부품 타입별 예외"를 코드에 넣기 시작하면 끝이 없다.

## 3차 — 렌더와 입력: 프레임워크의 함정 두 개

렌더는 고정 해상도 1600×900(레터박스), 1m = 100px. 그림 에셋이 아직 없으므로
모든 부품을 **물리 윤곽 그대로의 도형**으로 그린다 — 이 결정 덕에 "그림은 예쁜데
충돌이 어긋나 보이는" 문제를 원천 차단했고, 나중에 그림이 오면 파일만 넣으면
자동으로 교체되는 폴백 구조를 함께 만들었다.

**함정 1: 드래그 좌표가 두 배로 튀었다.** 프레임워크의 드래그 이벤트가 주는
"현재 위치(canvasEndPosition)"가 실제로는 `현재 + (현재 − 직전)`으로 계산돼
있어서, 손가락보다 이동량만큼 앞서 나갔다. 라이브러리 소스를 열어 확인한 실제
버그다. 시작 위치에 델타를 직접 누적하는 방식으로 우회했다.

**함정 2: 탭을 추가하니 드래그가 변했다.** 부품 선택(탭)을 게임에 붙이자 기존
트레이 드래그의 좌표 의미가 게임 전역에서 바뀌었다. 탭 인식기와 드래그 인식기가
**같은 제스처 아레나**에 들어가면서, 아레나 경합이 해소되는 첫 move 이벤트의
좌표 기준이 달라진 것. 이것도 근본 원인(인식기 등록 구조)을 소스로 확인하고,
두 경로 모두에서 수학적으로 같은 위치가 나오는 누적 방식으로 통일했다.

실기기(갤럭시 A16)에 올려 스크린샷으로 **도형 위치가 물리 좌표와 픽셀 단위로
일치**하는 것까지 확인하고 렌더 계층을 닫았다.

## 4차 — 편집 UX: 리뷰가 잡아낸 두 개의 조용한 버그

배치한 부품을 탭하면 선택 링 + 삭제 X + (회전 가능한 부품만) 회전 핸들이 뜬다.
회전은 5° 스냅. 트레이 남은 개수는 별도 카운터 없이 배치 목록에서 파생시켜
삭제 시 자동 복구되게 했다 — 상태가 두 곳이면 언젠가 어긋난다.

코드 리뷰에서 두 개가 걸렸다. 둘 다 조용히 잘못되는 종류였다.

1. **화면 맨 위에 놓은 부품은 삭제할 수 없었다.** 삭제 X가 부품 위 0.6m에 뜨는데,
   합법 배치 최상단(y=0.3)에서는 X의 히트 영역 전체가 화면 밖이었다. 버튼 위치를
   화면 안으로 클램프하는 함수 하나로 히트 판정과 렌더가 같은 좌표를 쓰게 고쳤다.
2. **삭제가 다른 부품의 각도를 오염시킬 수 있었다.** 회전 드래그 중(한 손가락)
   다른 손가락으로 그 부품을 삭제하면, 배치 목록 인덱스가 당겨지면서 회전 중이던
   인덱스가 **엉뚱한 부품**을 가리켰다. 삭제 함수 안에서 선택/회전 인덱스를 함께
   보정(같으면 해제, 크면 감소)하도록 한 곳에 모았다.

## 5차 — 화면 배선과 에디터

홈(월드 4 → 스테이지 10칸 그리드, 순차 해금) → 게임 → 클리어 시 다음 판으로,
마지막 판이면 홈으로. 설정에서 소리(저장만, 재생은 추후)와 언어(기기/한국어/영어).

**언어 전환이 조용히 안 먹혔다.** 루트에 리스너를 감아 전체를 리빌드시키려 했는데,
`const` 위젯은 정체성이 같아 프레임워크가 리빌드를 건너뛴다. 테스트가 먼저
실패해서 발견했고, 각 화면이 언어 상태를 직접 구독하는 구조로 바꿨다.

**엣지 투 엣지 대응.** 최신 안드로이드는 앱이 시스템 바 뒤까지 그리는 게 기본이라,
스크롤 목록에 시스템 바 여백을 더해주는 헬퍼를 만들어 마지막 항목이 내비게이션
바에 가리지 않게 했다(가족 앱에서 실제로 사용자가 겪었던 문제다).

**스테이지 에디터**는 디버그 빌드에서만 열린다. 모든 부품 무제한 + 지형·목표물
배치 + 목표 선택 + 같은 물리로 시험 실행 + **[솔루션 기록]**(현재 배치를 정답
데이터로 저장) + JSON 내보내기/가져오기. 40판을 좌표 숫자로 손으로 짜는 건
비현실적이라 콘텐츠 제작의 필수 도구다. 내보낸 JSON이 게임의 파서로 완전
왕복되는 것을 테스트로 못박았다.

**이 기계 특유의 함정도 하나.** 테스트를 기본 동시성으로 돌리면 다른 작업들과
메모리를 다투다 VM이 죽는다. `--concurrency=1`이면 안정적이다.

## 6차 — 첫 실기기 플레이테스트: 기계가 통과시킨 것을 사람이 떨어뜨렸다

40판·릴리스 빌드까지 끝내고 처음으로 폰에서 손가락으로 플레이한 날,
하루 만에 굵직한 결함이 다섯 개 나왔다. 전부 "테스트는 전부 통과"인 상태에서.

**실패했는데 아무 일도 안 일어나는 화면.** 부품 없이 ▶를 누르면 공이 1초 만에
화면 밖으로 사라지고, 게임은 실행 모드인 채 조용히 멈춰 보인다. 처음 하는
사람은 100% "고장"으로 읽는다. 목표 미달성 상태에서 움직일 물체가 다
사라지면 1.2초 뒤 자동으로 편집 모드로 돌아오게 했다.

**손가락 탭이 전부 죽어 있었다 — 이번 판 최대의 버그.** 부품 선택도, 회전도,
▶도 실제 손가락으로는 안 눌렸다. 원인: 탭 인식기와 드래그 인식기가 입력을
경쟁하는데, 포인터가 1픽셀이라도 움직이면 드래그 쪽이 가로챈다. 손가락은
반드시 몇 픽셀 흔들리므로 실기기에서 탭이 전멸 — 그런데 테스트와 개발용
기계 입력은 **이동량이 정확히 0**이라 전 과정에서 이 버그가 숨어 있었다.
탭 인식기를 아예 등록하지 않는 쪽으로 구조를 바꾸고(경쟁 자체를 소멸),
"15픽셀·0.3초 미만의 움직인 터치 = 탭"으로 드래그 스트림에서 탭을 합성했다.
이후 모든 입력 테스트는 **일부러 몇 픽셀 흔들리는 가짜 손가락**으로 짠다.
합성 입력 통과 ≠ 실터치 동작 — 이 저장소의 새 헌법이다.

**조작이 불편하다는 피드백 세 가지.** 놓은 부품을 고치려면 다시 탭해야 하고
(→ 놓자마자 자동 선택), 한 번 놓으면 옮길 수 없고(→ 잡아끌면 이동 — 두 번째
손가락이 이동을 가로채는 멀티터치 구멍은 리뷰가 잡아서 포인터 소유권으로
막았다), 회전 손잡이가 너무 작았다(→ 손잡이 확대 + 링 어디를 잡아도 회전.
이 과정에서 선풍기는 링이 자기 삭제 버튼을 항상 감싼다는 기하 문제가 나와
삭제 버튼 우선 가드를 넣었다).

**"3탄은 뭘 해야 할지 모르겠다."** 확인해 보니 버튼이 화면 밖 — 하단 트레이
바에 완전히 가려져 있었다. 전수 감사 결과 19판에서 24개 요소가 가려져 있었다.
물리 클리어(규칙 c)·배치 합법성(규칙 e)은 검증했지만 **"보이는가"는 검증한
적이 없었던 것.** 가시성 규칙(f)을 검증기에 추가하고 19판을 재조정했다.
검증 규칙은 이렇게 실패가 발견될 때마다 하나씩 늘어난다: 물리 → 배치 → 가시성.

**"깔끔한데 별로고, 저 네모 박스는 뭔지 모르겠다."** 배경·부품 그림은 예쁜데
UI 껍데기(트레이·버튼·목표 배지)가 무표정한 회색 박스라 서로 겉돌았다.
HUD 전체를 부품과 같은 스티커 재질(초콜릿 외곽선+캔디 색)로 다시 칠하고,
목표 배지는 깃발 달린 미션 카드로, 그리고 판에 들어설 때마다 **실제 목표물이
두 번 콩콩 커지는 연출**을 넣어 "저기에 넣는 거구나"가 말 없이 읽히게 했다.

이 라운드의 결론: 헤드리스 검증 파이프라인은 "풀 수 있는 게임"까지는
보장하지만, "사람 손에 쥐어줄 수 있는 게임"은 실기기에서 손가락으로
만져봐야 나온다. 둘 다 필요하다.

## 7차 — "물리는 되는데 왜 재미없지"를 다듬은 날

두 번째 플레이 감상은 뼈아팠다: "깔끔한 듯한데 조잡하고, 앵그리버드 같은
물리 손맛이 없다." 진단해 보니 물리 수치의 문제가 아니었다 — **물리가 잘
돌아간다는 사실이 눈에 안 보이는 것**이 문제였다.

**공이 구르는데 구르는 게 안 보였다.** 민무늬 원은 아무리 회전해도 정지 화면과
같다. 공 그림에 비대칭 무늬(고무공엔 흰 밴드, 쇠공엔 육각 볼트)를 넣는 것만으로
"데굴데굴"이 살아났다. 회전 각은 원래부터 물리와 동기화돼 있었다 — 보여줄
무늬가 없었을 뿐.

**부딪혀도 아무 일이 없었다.** 한 스텝에 속도가 크게 꺾이면(착지·충돌) 부품이
살짝 눌렸다 펴지고(스쿼시) 먼지가 퍽 나게 했다. 전부 뷰 계층에만 있는 연출이라
물리·검증은 1비트도 안 변한다. 앵그리버드 손맛의 8할은 이런 피드백이었다.

**부품들이 공중에 떠 보였다.** 지형이 무지 사각형이라 예쁜 배경 위에 붕 뜬
느낌 — 지형에 나무 판 질감을 입히고(그림이 오기 전엔 코드로 그림), 모든 부품
밑에 부드러운 그림자를 깔았다. 바닥이 생기니 비로소 "장소"가 됐다. 지형 타일
그림은 가로로 이어 붙는 심리스 조건이 핵심이라, 검수 때 좌우 끝 픽셀을 직접
비교해 이음새 차이 0을 확인하고 받았다.

홈 화면도 월드 카드에 배경 그림 썸네일과 진행 칩(n/10)을 달아 "고르는 맛"을
냈고, 스테이지 입장에 짧은 페이드를 넣었다.

이날의 교훈: 시뮬레이션의 정확함과 게임의 손맛은 다른 축이다. 정확함은
검증기가 지켜주지만, 손맛은 무늬 하나·먼지 한 줌·그림자 한 장이 만든다.

## 8차 — 출시 준비 완주

스토어 제출 패키지를 만들었다: 등록 문구(한/영 — 돈 이야기와 특정 상표를 쓰지

## 9차 — 상용화 UX·아트 폴리시

실기기에서 다시 보니 물리는 동작하지만 첫인상이 개발 빌드에 가까웠다. 홈은 기본
앱바와 설정 아이콘이었고, 트레이의 부품은 전부 같은 색 원으로 보였으며, 긴 판자를
선택하면 부품보다 훨씬 큰 점선 원이 떠 디버그 기즈모처럼 읽혔다. 클리어 화면도
`클리어!`와 아이콘 두 개뿐이라 과학 게임의 보상이 남지 않았다.

홈을 병아리 아이콘·태그라인·캔디 카드 상태가 있는 브랜드 셸로 다시 잡고, 게임에는
홈 버튼과 현재 월드·단계·목표·조작 안내를 넣었다. 트레이는 실제 부품 스프라이트를
비율에 맞춰 보여 주고, 직사각형 부품의 선택선은 실제 물리 윤곽을 따라가게 했다.
클리어는 큰 크림 카드 안에 재시도/다음 라벨과 목표별 과학 관찰 문장을 넣었다.

두 번째 실기기 검수에서는 UI가 아니라 부품 자체의 검은 면적이 문제였다. 14개
부품과 지형 타일을 새 아트 시스템으로 전면 교체했다: 검은 링 대신 슬림한 코코아색
선, 넓고 밝은 캔디 색면, 위쪽 밝은 면과 아래쪽 그늘 면의 소프트 셀 셰이딩. 공은
회전 밴드, 쇠공은 볼트, 기어류는 색과 동력 표식처럼 기능 판독 표시는 더 크게
남겼다. 지형 타일은 좌우 끝 픽셀 차이 0으로 다시 맞췄다.

실제 PNG가 늘면서 첫 프레임 이미지 디코딩이 트레이의 DragCallbacks 마운트를
잠깐 막는 테스트 레이스도 드러났다. 슬롯 입력은 즉시 마운트하고 그림만 비동기로
갈아 끼우게 바꿔 첫 터치가 이미지 로딩에 종속되지 않게 했다.

갤럭시 A16에서 홈 → 배치 → 80° 회전 → 물리 실행 → 바구니 클리어를 다시
완주했고 스토어 스크린샷 6장도 새 화면으로 교체했다. 최종 게이트는 `flutter
analyze` 0건, 전체 101개 테스트 통과, 릴리스 APK 빌드 성공이다.

## 10차 — 정답만 맞히던 판을 다시 하고 싶은 실험으로

아트와 조작은 많이 좋아졌지만 한 번 풀고 나면 다시 열 이유가 약했다. 이번에는
기존 40판을 버리지 않고 세 가지 재미 루프를 얹었다.

첫째, 대표 판 세 곳에 **연쇄 반응 리본**을 달았다. 공→도미노→목표처럼 현재
장치가 어떤 순서로 움직일지 실제 부품 그림과 점선으로 미리 보여 준다. 새 물리를
추가한 것이 아니라 이미 있던 인과관계를 읽히게 만든 변화다.

둘째, 뒷마당 5단계를 **예측하고 실험하는 판**으로 바꿨다. 고무공/쇠공 중 결과를
먼저 고르기 전에는 실행할 수 없고, 클리어 화면에서 예측과 결과가 같았는지 바로
돌려준다. 과학 설명을 결과 뒤에만 읽는 구조에서 가설→실험→관찰 구조로 한 단계
올라갔다.

셋째, 모든 클리어에 1~3성 숙련도를 저장한다. 기본 클리어 1성, 부품 수 제한이나
예측 성공 1성, 판 안의 민트 수집별 획득 1성이다. 별은 보너스 센서라 목표 달성을
막지 않으며, 기존 사용자의 `cleared_v1` 기록은 갑자기 0성처럼 보이지 않도록
3성으로 보존한다. 새 결과는 별점을 먼저 저장한 뒤 클리어 표식을 저장해 이 레거시
보정과 충돌하지 않게 했다.

민트 수집별은 투명 PNG 실에셋으로 만들었고, 월드 1·3의 10단계 정답 경로가 실제로
별 센서를 통과하면서도 클리어되는지 헤드리스 물리 테스트로 고정했다. 갤럭시 A16에서
예측 선택→쇠공 배치→실행→3성 결과, 연쇄 리본, 별 도전과 필드 수집별을 실터치로
검수했다. 결과 카드의 과학 문장과 버튼이 닿던 간격도 실기기 화면에서 발견해 수정했다.

최종 게이트는 `flutter analyze` 0건, 전체 113개 테스트 통과다.

## 11차 — 첫 판 앞에서 막히지 않는 실험 수첩

게임이 재미있어져도 첫 화면의 짧은 조작 문장 하나만으로는 어린 플레이어가
`목표 확인 → 부품 배치 → 회전 → 실행` 순서를 한 번에 이해하기 어려웠다. 첫
스테이지 첫 방문에만 자동으로 열리는 **삐약 박사의 실험 수첩**을 추가했다.

안내는 네 장이다. ① 현재 판에 맞는 실제 목표물 그림으로 미션을 보여 주고, ② 실제
판자와 손가락 아이콘으로 끌어놓기를 설명하고, ③ 기울어진 판자와 회전 아이콘으로
노란 손잡이를 알려 주고, ④ 실행 버튼과 수집별로 실험·재도전의 의미를 설명한다.
글만 넘기는 설명서가 아니라 기존 부품이 살짝 콩콩 움직이고 페이지가 미끄러져
바뀌는 작은 놀이처럼 만들었다.

완료·건너뛰기는 `tutorial_seen_v1`에 저장되어 다음 방문을 방해하지 않는다. 대신
모든 스테이지 우상단에 노란 전구 도움말 버튼을 두어 언제든 네 장을 다시 볼 수
있다. 안내를 닫으면 실제 목표물이 다시 펄스해 설명에서 플레이로 시선이 자연스럽게
이어진다. 한/영 문구와 48px 이상 버튼, 780×360 가로 화면 레이아웃을 테스트했다.

도움말의 첫 그림은 현재 목표에 맞춰 공→바구니, 쇠공→버튼, 풍선→압정,
공→도미노로 바뀌므로 다른 판에서 다시 열어도 잘못된 목표를 가르치지 않는다.

최종 자동 게이트는 `flutter analyze` 0건, 전체 116개 테스트 통과다.

## 12차 — 한 월드 20판, 총 80판으로 확장

네 월드를 각각 10판에서 20판으로 늘렸다. 11~20단계는 앞에서 배운 장치를
반대편으로 옮기거나 진행 방향을 뒤집어 다시 조립하는 **숙련 리믹스**다. 단순히
파일만 복제하지 않고, 모터 톱니처럼 회전 방향이 결과를 바꾸는 장치는 내부 구조를
유지한 채 무대 반대편으로 이동했다. 도미노·다단 장치는 연쇄 반응 표식을 더하고,
재료를 고르는 판에는 실행 전 예측, 모든 후반 판에는 정답 부품 수 기준 별 도전을
넣었다. 후반 판은 정답보다 여분 부품을 하나 더 줘서 처음에는 자유롭게 실험하고,
재도전에서는 더 간결한 장치로 줄일 수 있게 했다.

홈 카드에 20칸을 네 줄로 눌러 넣으면 짧은 가로형 휴대폰에서 터치 영역이 작아져서,
기존 5×2 버튼 크기를 유지한 `1–10 / 11–20` 페이지 전환기를 제목 줄에 넣었다.
진행 칩은 월드별 `n/20`과 누적 별 수를 계속 보여 준다.

새 40판은 원본 정답뿐 아니라 x±0.05m·각도±2° 손가락 오차 세 종류까지 모두
시뮬레이션했다. 첫 검수에서 반전된 3판이 탈락했고, 장치를 재배치하고 다시 돌려
최종 80/80판이 정답 클리어·오차 강건성·비자력 클리어·배치 합법성·가시성 검사를
전부 통과했다. 후반 판을 다시 만들 수 있는 생성 규칙은
`tool/generate_expert_stages.dart`에 남겼다(다음 차수에서 복합 장치 생성기로 확장).

릴리스 APK를 갤럭시 A16에 기존 기록을 유지한 채 설치했다. 홈에서 기존 클리어가
`10/20`으로 보이고, `11–20` 페이지의 11단계만 정상 해금되는 것을 확인했다.
11단계는 실제 손가락 드래그·80° 회전·실행으로 클리어해 최소 부품 도전 3성까지
저장했다.

최종 자동 게이트는 `flutter analyze` 0건, 전체 121개 테스트 통과다.

## 13차 — 반전 리믹스를 숙련자용 복합 장치 40판으로 교체

처음 만든 11~20단계는 방향 전환과 여분 부품 도전은 있었지만, 40판 중 32판의
정답이 부품 하나라서 "여러 기믹을 조립하는 숙련자 구간"이라고 부르기 부족했다.
오너 피드백 뒤 후반 40개 JSON을 전부 다시 설계했다.

아이 방은 시작 공까지 직접 싣고 판자 경사·다리·도미노 릴레이를 완성한다. 뒷마당은
시소+쇠공, 2연속 트램펄린, 시소+쇠공+트램펄린, 다중 풍선+압정을 섞었다. 공장은
완성돼 있던 모터를 트레이로 내리고 모터+일반 톱니+패들 전달계를 직접 맞물리게
했으며, 트램펄린이나 압정까지 이어진다. 우주는 선풍기+공, 선풍기+시소+공,
모터+패들+선풍기, 모터+패들+트램펄린, 두 선풍기로 떨어진 도미노 두 무리를 각각
쓰러뜨리는 판, 판자+선풍기+톱니+압정 종합 장치로 구성했다.

후반 40판은 전부 정답 부품 2개 이상, 35판은 서로 다른 부품 종류 2개 이상,
12판은 3~4개 부품을 쓴다. 플레이어 정답에는 판자·두 공·시소·모터/일반/패들
톱니·선풍기·트램펄린·압정까지 10종이 실제로 등장한다. 더 중요한 새 게이트는
**정답 부품 하나씩 제거하기**다. 40판의 모든 정답에서 각 부품을 하나씩 빼고
물리를 다시 돌려 모두 실패하는지 검사해, 클리어에 필요 없는 장식용 도구가 하나도
남지 않게 했다.

생성기는 `tool/generate_expert_stages.dart`로 이름을 바로잡았다. 80판 전체가 원본
정답과 x±0.05m·각도±2° 오차 세 종류, 배치 합법성, 비자력 클리어 검사를 다시
통과했다.

최종 자동 게이트는 `flutter analyze` 0건, 전체 122개 테스트 통과다.

갤럭시 A16에서는 검수용 전체 해금 릴리스로 w3_s12를 열어 모터→일반 톱니→패들
세 부품을 직접 드래그·스냅하고 3성 클리어했다. 검수 뒤에는 전체 해금 옵션이 없는
일반 릴리스를 다시 빌드·설치해 순차 해금 상태로 돌려놓았다.

## 14차 — 부품 개수가 아니라 우회 불가능성으로 숙련판 재설계

13차 결과는 부품 수는 늘었지만 핵심 난이도 검수가 틀렸다. 바구니 목표에서 공을
트레이에 함께 넣어 둔 판은 장치를 만들 필요 없이 공을 바구니 위에 놓으면 끝났다.
"정답 부품 하나씩 제거" 검사도 기록된 정답만 확인했을 뿐, 전혀 다른 한 부품
우회 해법은 찾지 못했다.

후반 40판의 저작 원칙을 다시 세웠다. 바구니·버튼·도미노 목표에서는 공을 트레이에
주지 않고 시작점 프리셋에 고정한다. 풍선 목표에서는 압정을 프리셋에 고정해 풍선이
그곳까지 이동하도록 한다. 월드 1은 시작 공 뒤에 2~3개의 끊어진 교량과 발사 경사를
조립하는 장거리 코스, 월드 2는 고정 쇠공이 시소를 때린 뒤 두 트램펄린을 연속으로
타는 코스와 양쪽 상승 풍선을 각각 판자 두 장으로 유도하는 코스, 월드 3은 모터부터
패들까지 4~5개의 톱니를 직접 맞물리는 코스, 월드 4는 팬+판자, 팬+시소+트램펄린,
모터+패들+팬, 양쪽 풍선용 판자+팬+톱니 장치로 교체했다.

새 `tool/audit_expert_shortcuts.dart`는 각 숙련판의 트레이 부품 하나를 목표물·시작
물체 주변과 화면 전체 대표 좌표, 회전 가능한 여러 각도에 실제로 놓고 700스텝씩
시뮬레이션한다. 첫 실행에서 트램펄린 하나, 판자 하나, 팬 하나로 끝나는 우회 6판을
찾아 모두 불합격 처리했다. 해당 판을 3단 장치 또는 좌우 두 목표 장치로 바꾼 뒤
재실행한 결과 샘플 단일 부품 우회는 0건이다.

최종 후반 40판은 전부 목표 직행 부품 지급 금지, 37판이 정답 3개 이상, 26판이
서로 다른 도구 2종 이상이다. 기존의 정답 부품 하나씩 제거 검사도 계속 유지하고,
80판 원본 정답·x±0.05m 지터·회전 가능한 판자/선풍기 각도±2°·비자력·배치
합법성 검사를 다시 통과했다.

A16에서 새 시소 코스를 직접 배치하려던 중 트램펄린 solution에 -4°가 적힌 문제도
발견했다. 게임은 트램펄린·시소·톱니를 회전시킬 수 없으므로 자동 시뮬레이션만
통과하고 사람은 만들 수 없는 정답이었다. 회전 불가 부품의 정답 각도를 0°로
강제하는 검증을 추가하고, 해당 뒷마당 8판·공장/우주 관련 판과 기존 w2_s06까지
전부 0° 배치만으로 다시 튜닝했다. 지터도 실제 회전 가능한 판자·선풍기에만 각도
오차를 적용한다.

최종 자동 게이트는 80/80 스테이지 검증, 샘플 단일 부품 우회 0건,
`flutter analyze` 0건, 전체 124개 테스트 통과다. 일반 릴리스 APK를 A16에
재설치하고 w2_s11에서 트레이의 시소와 트램펄린 두 개를 실제 손가락 드래그로
0° 배치한 뒤 `시소→1차 반동→2차 반동→바구니` 3성 클리어까지 확인했다.

## 15차 — 전수 감사로 복제 콘텐츠를 걷어내고 최종 챕터 "삐약 연구소"를 열다

"더 어렵게 만들고 싶은데, 지금 판들이 도구만 잔뜩 주는 건 아닌가"라는 의심에서
출발해 80판 전체를 기계로 전수 감사했다. 정답에서 부품을 하나씩 빼 보고(minus-one),
부품 하나만 단독으로 놓아 보고, 좌표를 배율을 올려 가며 흔들어 오차 허용치를 재고,
모든 판 쌍의 좌표 차가 상수 이동/미러로 수렴하는지 검사하는 스크립트를 돌렸다.

결과는 의심과 반대였다. 트레이 여분은 전 판 정확히 1개 — 별 도전(부품 제한)용
의도된 설계였고, 빼도 클리어되는 진짜 장식 부품은 80판 중 단 1건(`w4_s08`의
톱니)이었다. 대신 예상 못 한 문제가 드러났다. **복제였다.** 월드1 후반 7판은 한
코스의 좌우 미러, 월드2 후반 8판은 시소+트램펄린 한 구조를 옆으로만 민 것(28쌍
검출), `w4_s12`와 `w4_s16`은 좌표가 소수점까지 일치했다. 그리고 난이도의 실체가
"발상이 어려움"이 아니라 "배치 오차 허용치가 0.05m로 좁음", 즉 손끝 난이도라는
것도 수치로 확인됐다.

그래서 세 갈래로 고쳤다.

**복제 정리.** 월드1 후반 9판을 주머니 가두기·계단식 도미노 폭포·지하통로·역주행
같은 서로 다른 경로 이야기로 다시 설계했고(사라졌던 도미노 목표도 2판 복원),
월드2 후반 8판도 전부 갈아엎으면서 이 월드의 정체성인 **무게 함정**을 심었다 —
쇠공과 고무공을 나란히 주는데 낮은 천장 판은 고무공이 튀어 갇히고, 되튐 턱 판은
쇠공이 멈춘다. 잘못 고르면 실패한다는 걸 양 재질 500여 지점 낙하 스윕으로
증명했다. 월드4의 남은 쌍둥이 3판은 바람 우물(하강풍으로 풍선을 가시밭에 누르기)·
바람 기중기·7단계 졸업 세탁 라인으로 교체했다. 이제 100판 중 서로 겹치는 판은
0쌍이고, 다시 만든 판들의 오차 허용치는 평균 0.05에서 0.10~0.17로 올라갔다 —
어려움은 손떨림이 아니라 머리에서 나와야 한다.

**숨은 UI 결함 수정.** 연쇄 리본과 도전 리본이 같은 좌표에 겹쳐 그려지던 10판,
예측 패널이 있으면 부품 제한 힌트가 아예 숨던 4판을 리본이 스스로 빈자리를 찾아
쌓이는 방식으로 고쳤다(겹침 없음을 위젯 테스트 4건으로 고정).

**최종 챕터 신설.** 다섯 번째 월드 **"삐약 연구소"** 20판을 손으로 새로 설계했다.
설계 헌법: 부품 3~5개가 전부 일해야 하고(하나 빼면 실패를 전 판 기계 증명), 서로
다른 기믹 가족 2~3개를 조합해야 하며, 오차 허용치 0.10 미만 판은 이 월드에
존재할 수 없다. 그럴듯하지만 틀린 미끼를 6판에 심고 전부 시뮬레이션으로 실패를
증명했다 — 참호 덕트는 쇠공만 통과하고, 같은 바람에 가벼운 공만 간극을 건너고
(F=ma), 눈앞의 압정으로 직접 불면 립에 막힌다. 회전문이 풍선을 쳐 보내는 판,
기어 열이 벽의 창을 관통해 동력을 전달하는 판처럼 앞 80판에 없던 결합을 우선
탐색했고, 마지막 20단계는 마개 공이 새장을 열면 풍선이 삼단 S자 페리를 타고
부력 저울이 버튼을 누르는, 부품 5개짜리 게임 전체의 졸업시험이다. 홈에는 칠판
초록 카드와 실험실 배경이 걸리고 월드4 마지막 판을 깨야 열린다.

최종 자동 게이트는 100/100 스테이지 검증(정답+오차 3변형·비자력·배치 합법성·
가시성), 전 월드 복제 0쌍, 정답 부품 전수 필수성 증명, `flutter analyze` 0건,
전체 137개 테스트 통과다.

## 16차 — 화면에 보이지 않는 것들, 그리고 14개 언어

실기기로 100판을 훑다가 아이 방 13단계에서 손이 멈췄다. 목표는 도미노 쓰러뜨리기,
안내 리본에는 "공 → 도미노 → 도미노"라고 그려져 있는데, **화면 어디에도 공이
없었다.** 시작 공이 안내 리본 뒤에 100% 가려져 있었다. 물리 검증도, 배치 검증도,
지터 검증도 전부 통과한 판이었다.

원인은 검사의 사각지대였다. 가시성 규칙(f)은 **아래쪽 트레이 바만** 보고 있었고,
위쪽 목표 배지·안내 리본·예측 패널, 오른쪽 실행 버튼, 그리고 화면 경계 자체는
아무도 검사하지 않았다. 그래서 HUD 사각형들을 좌표로 적어 넣은 감사 스크립트를
만들어 100판을 훑었다. **가려진 물체 50건**이 나왔다. 압권은 풍선 목표 두 판으로,
터뜨릴 압정이 화면 위쪽 바깥(y = −0.5, −1.0)에 있었다 — 플레이어는 무엇을 향해
풍선을 올려야 하는지 알 수 없고, 풍선은 화면 밖으로 사라진 뒤 터졌다.

고치는 방향은 두 갈래였다.

**UI 쪽**: 홈·도움말 버튼은 게임 캔버스 위에 떠 있는 위젯이라 어디에 두든 그 자리의
부품을 덮는다. 화면 아래 150px 띠는 트레이 바가 이미 차지해 **어떤 스테이지도 쓰지
않는 유일한 공간**이라, 그리로 내렸다. 이것만으로 가림 8건이 사라졌다. 같은 검수에서
"세운 판자를 옮기려는데 자꾸 지워지는" 문제도 잡았다. 삭제 X가 부품 중심 위 0.6m
고정이었는데, 판자를 세우면 부품이 위아래로 1m라 X가 판자 몸통 안에 들어앉아 이동
드래그를 전부 가로챘던 것이다. 부품의 회전 반영 높이에 맞춰 바깥으로 밀어냈다.

**스테이지 쪽**: 18판을 옮겼다. 중요한 발견은 **판 전체를 한 벡터로 평행이동하면
물리가 그대로**라는 점이다 — 중력이 균일하고 시뮬레이션이 절대좌표에 의존하지
않으니, 스텝 수와 지터 마진이 소수점까지 같다. 난이도를 건드리지 않고 자리만
비킬 수 있었다. 자리가 없는 판만 실제로 재조정했다. 부작용은 오히려 이득이었다:
가려져 있던 자리는 배치도 까다로운 자리여서, 아이 방 5단계는 손 떨림 허용치가
0.05 → 0.30으로 여섯 배 넓어졌고 우주 3·10·13단계도 두 배씩 넓어졌다.

마지막으로 이 모든 것을 **검사 규칙 (g)** 로 승격했다. 목표 배지·연쇄/도전 리본·
예측 패널·실행 버튼의 사각형과 캔버스 경계를 스테이지 저작 규칙으로 못 박고,
일부러 규칙을 어긴 판 3개를 픽스처로 넣어 검사기가 실제로 잡는지 고정했다.
지형(플랫폼)이 화면 옆으로 이어지는 것만 예외다 — 그건 배경이 계속된다는 표현이다.

**그리고 14개 언어.** 한국어·영어 두 벌이던 문자열 표를 언어별 파일로 쪼개고
12개를 더했다(일본어, 중국어 간체·번체, 스페인어, 포르투갈어, 독일어, 프랑스어,
이탈리아어, 러시아어, 인도네시아어, 베트남어, 태국어). 설정에서 고르며, 각 언어는
그 언어 자신의 이름으로 보여 준다 — 아이는 읽을 수 없는 남의 언어 이름 대신
자기 글자의 생김새를 찾는다. 기기 언어 자동 인식은 대만·홍콩·마카오를 번체로
가른다.

번역에서 진짜 어려운 건 뜻이 아니라 **폭**이었다. 홈 화면 월드 이름 칸은 148px에
한 줄 말줄임이라, 독일어 "Spielzeugfabrik"과 러시아어 "Фабрика игрушек"이 잘린다.
글자 수 규칙 대신 렌더 위치를 코드에서 찾아 실제 픽셀 폭으로 검산했고, 넘치는
것은 "Spielzeugwerk", "Цех игрушек"처럼 뜻을 지키며 줄였다. 부품 제한 라벨은
코드가 숫자를 뒤에 붙여 그리므로 그 어순에서 자연스러운 표현을 골랐다(일본어는
조수사 때문에 어순 자체가 불가능해 라벨:값 형태로 갔다).

실기기에서 독일어로 돌려 홈·게임·리본·트레이 제목을 확인했고, 태국어 글자까지
깨짐 없이 렌더링되는 것을 봤다. 언어 전환은 앱 재시작 없이 즉시 반영된다.

최종 자동 게이트는 100/100 스테이지 검증(규칙 a–g), 가림 감사 0건,
`flutter analyze` 0건, 전체 149개 테스트 통과다.

## 17차 — 출시 직전, 스크린샷이 잡아낸 것들

번역을 다 넣고 "이제 됐다" 싶을 때, 실기기 스크린샷을 언어별로 모아 놓고
한 장씩 들여다봤다. 화면이 말해 준 것은 문자열 표를 아무리 봐도 안 보이는
것들이었다.

**태국어 홈 화면에 `สนามหลังบ้...` 이라고 찍혀 있었다.** 월드 이름이 잘린
것이다. 독일어는 `Kinderzim…`, 베트남어는 `Phòng của…`. 원인을 따라가 보니
번역이 길어서가 아니었다. 제목 칸은 같은 줄에 페이지 전환기와 진행도 칩을
같이 두는데, **별을 모을수록 진행도 칩이 넓어져 제목 칸이 좁아진다.** 즉 잘
돌아가던 이름도 플레이어가 별을 모으면 어느 순간 잘리기 시작한다. 번역을
짧게 다듬는 것만으로는 다음 언어에서 또 터질 자리였다. 제목을 **자르는 대신
줄여서 넣도록** 바꿨다(`FittedBox`). 이름은 온전히 남고, 칸이 좁아지면 글자만
조금 작아진다.

**어조와 오역도 화면에서 잡혔다.** 포르투갈어는 예측 성공을 "네 *찍기*가
맞았다"(palpite)라고 말하고 있었다 — 예측하고 실험하고 관찰하는 법을 가르치는
화면에서 스스로 개념을 깎아먹는 낱말이다. 독일어는 같은 공을 화면마다
`Kugel`과 `Ball`로 번갈아 부르고 있었고, 베트남어는 "초록 버튼"이라 했는데
`xanh`는 파랑과 초록을 같이 뜻하는 말이라 `xanh lá`로 못 박았다. 스페인어는
"밀어 내린다"에서 전치사가 빠져 있었다.

**`▶` 기호는 언어마다 다르게 그려졌다.** 한국어·중국어·일본어에서는 검은
삼각형인데, 라틴·키릴·태국 문자에서는 시스템 글꼴 대체 때문에 **주황색
이모지**가 나온다. 그런데 튜토리얼 문장은 "**초록** ▶를 누르세요"라고 색을
지목하고 있었다 — 글은 초록, 옆의 기호는 주황. 글자 표현 선택자(U+FE0E)를
붙여 봤지만 안드로이드는 무시했다. 그래서 반대로 갔다: 튜토리얼 그림이 이미
초록 동그라미와 재생 삼각형을 크게 보여 주고 있으니, **글에서 색 주장을 빼고**
"재생 버튼"이라고만 하게 아홉 언어를 고쳤다.

**출시 자료는 형제 앱들의 자리로 옮겼다.** 등록정보 15개 언어와 출시 노트를
`legal/peepscience/` 에 두고, 앱 저장소에는 어디를 보라는 안내만 남겼다 —
앱 소스는 언젠가 비공개가 될 수 있어도 출시에 필요한 것은 공개 저장소에
남아야 한다. 글자 수는 스크립트로 검사한다(앱 이름 30·짧은 설명 80·자세한
설명 4000). 처음 돌렸을 때 영어 짧은 설명이 84자로 걸려 바로 줄였다.

문구 규칙도 형제 앱에서 하나 더 배웠다. 광고·무료 이야기를 쓰지 않는 것은
알고 있었는데, **"오프라인 전용·인터넷 안 씀·개인정보 수집 안 함"도 쓰지
않는다.** 지금은 참이어도 나중에 거짓이 되고, 그때 문구를 지워도 그것을 보고
받은 사람은 남기 때문이다. 열네 언어 초안에 그 문장이 들어가 있어 전부
걷어냈다.

마지막으로 언어별 스크린샷 56장을 고친 빌드로 다시 찍었다. 서명은 형제 앱들과
같은 업로드 키를 쓴다(인증서 지문 일치 확인).

최종 자동 게이트는 100/100 스테이지 검증, `flutter analyze` 0건, 149개 테스트
통과, 등록정보 45건 글자 수 통과다.

## 18차 — 자기 번역을 자기가 검토하면 안 된다

열네 언어를 다 넣고 "번역 검수 완료"라고 적었다. 그런데 그 검수를 **번역을 쓴
쪽이 했다.** 일본어·중국어는 "한 글자도 안 고쳤다"는 결론이 나왔고, 영어는 아예
처음 작성된 뒤로 아무도 본 적이 없었다. 기계 감사(키 누락·자리표시자·한글 잔존)는
통과했지만 그건 **모양만** 보는 검사다. 뜻이 어긋난 문장은 애초에 대상이 아니다.

그래서 그 번역을 쓰지 않은 쪽에 다시 맡겼다. 방법은 **되번역 대조** — 문장을
한국어로 되돌려 원문과 한 줄씩 맞추고, 실기기 스크린샷을 열어 문맥에서 읽고,
같은 개념을 화면마다 같은 낱말로 부르는지 보는 것. 그리고 "앞의 결론을 믿지 말고
의심하는 쪽으로 읽으라"고 명시했다.

**여덟 개 언어에서 열아홉 줄이 나왔다.**

가장 컸던 것은 라틴어권 네 언어에서 **"모두"가 통째로 빠진 것**이다. `풍선을
모두 터뜨려라`가 `풍선을 터뜨려라`가 되어 있었다. 나머지 열 언어에는 전부 있었고,
스페인어는 도미노에는 `todos`가 있는데 풍선에만 없었다 — 한 언어 안에서 어긋나
있었으니 실수라는 증거다. 아이에게 "몇 개를 터뜨려야 끝나는가"는 규칙 그 자체다.

**없는 동작을 있다고 말하는 문장도 있었다.** 포르투갈어·프랑스어 튜토리얼이
미션 카드를 누르면 목표물이 "뛰고 손을 흔든다"고 했는데, 코드를 보면 크기만 두 번
부풀렸다 줄이는 게 전부다. 아이가 없는 걸 찾게 된다.

**영어가 가장 나빴다.** `Peep Professor's Lab Notes`는 영어 어순으로 "삐약들을
가르치는 교수"로 읽히고(일본어 `ピープ博士`·중국어 `皮普博士`는 제대로 돼 있었다),
별 도전 리본은 `Use no more than  3` 이라 **3이 무엇의 3인지 명사가 없었다.**
`air forces`는 공군으로 먼저 읽히고(독일어 `Luftkräfte`도 같은 함정이었다),
`bounce and wave`는 원문에 없는 동작이었다.

러시아어에는 비문이 있었고(`играть`는 그렇게 목적어를 받지 못한다), 태국어는
띄어쓰기 하나가 빠져 "실패하면"이 "부품을 놓치면"으로 붙어 읽혔다. 포르투갈어
과학 문장은 "힘은 물체를 움직일 **수 있어요**"가 "움직인다"는 단정으로 바뀌어
있었다 — 열두 언어 모두 조동사를 갖고 있는데 하나만 빠진 것이다.

**성별도 고쳤다.** 스페인어·이탈리아어·프랑스어 튜토리얼 부제가 "너도 이제
과학자!"를 남성형으로 쓰고 있었다. 플레이어의 절반은 여자아이다. 스페인어·
이탈리아어는 성중립 명사가 아예 없는 언어라 명사(정체성) 대신 행위로 바꿨고
(`ya haces ciencia` — 너 벌써 과학을 하고 있잖아), 프랑스어는 `scientifique`가
원래 남녀 공용이고 관사만 남성이라 관사를 뺐다.

**일본어와 중국어는 이번에는 진짜로 검증됐다.** 쉰한 문장을 되번역 대조해 오류가
0건이었고, 오히려 세심했다 — 일본어는 학년별 한자 배분을 지켜 초등 6학년 한자인
`裏`·`宇宙`는 가나로, 3학년 이하인 `部屋`·`工場`은 한자로 썼다. 번체 중국어는
대만 어휘를 제대로 갈랐다(`設定`·`主畫面`·`彈簧床` — 본토 표현이 아니다).

교훈은 하나다. **검토는 쓴 사람이 아닌 사람이 해야 한다.** 자기 문장은 다시 봐도
괜찮아 보인다. 그리고 기계 감사가 통과했다는 말은 "모양이 깨지지 않았다"는
뜻이지 "뜻이 맞다"는 뜻이 아니다.

이번 라운드에서 스토어 문안도 여섯 군데 고쳤다. 영어 설명의 "읽기가 전혀 필요
없다"는 원문("글자를 몰라도 아이콘으로 이해할 수 있도록")보다 센 단정이었고,
인도네시아어는 화면 폭 때문에 줄인 월드 이름 `Halaman`이 줄글에 그대로 흘러가
"페이지"로 읽히고 있었다.

## 19차 — 보이는 대로 판정하기, 그리고 감사기를 오래 안 돌린 대가

실기기에서 "톱니 옆에 놓으려는데 여긴 되고 저긴 안 된다"는 제보를 받았다.
확인해 보니 배치 가능 판정이 모든 부품을 **축에 나란한 사각형**으로 바꿔서
보고 있었다. 반지름 0.5m짜리 톱니는 1×1m 정사각형이 되어 대각선 모서리가 원
밖으로 0.2m 튀어나오고, 45도로 기울인 널빤지(2.0×0.24m)는 1.58×1.58m 상자가
된다. 화면에는 빈 곳인데 빨간불이 뜨는 자리가 그렇게 생겼다.

판정을 **실제 모양**으로 바꿨다. 원끼리는 중심거리, 원과 회전한 사각형은
사각형 안쪽 최근접점까지의 거리, 사각형끼리는 분리축 정리. 노 달린 톱니는
톱니와 노의 합집합이라 둘 중 하나만 닿아도 겹침으로 본다. 사각형 판정은
버리지 않고 **싼 1차 통과**로 남겨 뒀는데, 덕분에 새 규칙이 옛 규칙보다
엄격해지는 일이 구조적으로 불가능하다 — 실제 모양은 언제나 그 사각형 안에
들어가기 때문이다. 놓을 수 있는 자리가 약 13% 넓어졌고, 프레임당 비용은
337ns → 491ns로 60fps 한 프레임의 0.003%다.

**되돌림 확인에서 테스트의 구멍이 하나 드러났다.** 일부러 코드를 일곱 가지로
망가뜨려 테스트가 실제로 빨개지는지 봤는데, 분리축 하나를 빼는 세 가지
변형이 아무것도 잡지 못했다. 원인은 내 첫 사각형-사각형 테스트가 서로 수직인
널빤지 두 개를 썼다는 것이었다 — 두 사각형의 축 집합이 겹쳐서, 상대편 축을
아예 무시하는 구현도 통과한다. 45도와 15도로 어긋난 쌍을 넣자 그제야 빨개졌다.

그리고 더 큰 것이 나왔다. 지름길 감사기(`tool/audit_expert_shortcuts.dart`)를
돌려 보니 **부품 하나만 놓아도 클리어되는 판이 열 개** 있었다. 그중 아홉은
내 판정 수정과 무관하게 **전부터 있던 것**이다. 이 감사기는 스테이지가
80판이던 시절 이후로 한 번도 돌지 않았는데, 그 사이 월드1·2 탈복제, 월드4
재설계, 월드5 20판 신설, HUD 가림 이동이 전부 이 검사 없이 지나갔다. 나머지
한 판(뒷마당 15단계)은 내 수정 때문에 새로 열렸다 — 프리셋 경사로가 예전에는
부풀려진 사각형으로만 그 자리를 막고 있었고(막던 폭 0.564m 대 실제 여백
0.463m), 판정이 정확해지자 화면상 비어 있던 그 자리가 진짜로 열린 것이다.

교훈은 앞 차수와 같은 종류다. **한 번 만든 감사기는 계속 돌려야 감사기다.**
게이트에 걸어 두지 않은 검사는 조용히 죽는다. 열 판을 막는 작업은 다음
차수로 넘긴다.

같은 라운드에서 힌트 문장도 고쳤다. 회전 손잡이는 널빤지와 선풍기에만
붙는데, 트레이에 그런 부품이 없는 판이 100판 중 39판이다. 그 판에서도
"노란 손잡이로 돌린 뒤"라고 안내하고 있었으니 아이가 있지도 않은 손잡이를
찾게 된다. 트레이를 보고 두 문장 중 하나를 고르게 했고, 새 문장은 14개 언어
모두 기존 힌트에서 회전 절만 덜어낸 것이라 문체가 튀지 않는다.

## 20차 — 부품 하나로 뚫리던 열 판을 막다

지름길 감사기가 잡아낸 열 판을 네 팀으로 나눠 고쳤다. 감사기는 성긴 격자
(앵커 × 7 × 5 × 각도)만 훑으므로, 잡힌 그 한 점만 막으면 옆 칸으로 도망갈
뿐이다. 그래서 판마다 **구조**를 손봤고, 각 판을 0.1~0.2m 격자 × 전 각도로
다시 훑어 클리어 0을 확인한 뒤에야 닫았다(합계 백만 단위 배치, 전부 0).

수법은 판마다 달랐다. 뒷마당 12단계는 바구니를 천장 바로 밑에 넣어 **위쪽에
공을 놓을 자리 자체를 없앴다.** 아이 방 14단계는 어떤 지붕으로도 정답 궤적과
지름길 궤적을 가를 수 없어서(36개 지름길이 정답을 양쪽에서 감싸고 있었다),
오른쪽 절반을 **속도 필터**로 바꿨다 — 낙하 에너지를 그대로 가진 공은 낭떠러지를
날아 넘어가 도미노를 지나쳐 버리고, S자 곡선에서 느려진 공만 관문 아래로
떨어져 도미노에 닿는다. 연구소 14단계와 보스판 20단계는 **시소가 들어갈 수
없는 폭**으로 복도를 좁혔고, 연구소 17단계는 활주로를 바구니까지 이어 붙이고
지붕을 덮어 터널로 만들었다(지붕 밑 틈 0.63m, 배치 최소 0.64m).

**바람은 지형을 뚫는다.** 이 엔진에서 선풍기 바람은 영역 판정만 하므로 벽
너머의 물체도 민다. 서 있는 도미노는 어느 방향 바람에도 바닥 마찰 토크로
제자리에서 넘어진다. 연구소 12단계는 여덟 가지 지형 변형을 실측한 끝에
"바람은 못 넘기고 공은 넘기는" 지형이 존재하지 않는다는 결론이 나서, 공의 경로는
한 좌표도 안 바꾸고 **목표를 도미노에서 바구니로** 바꿨다. 16단계는 반대로
**선풍기를 트레이에서 뺐다.** 규칙 하나가 남았다: 선풍기가 있는 판에 도미노
목표를 두지 않는다.

**버튼 위 4cm 띠.** 버튼의 누름 센서는 배치 여유(0.02m)보다 0.05m 높이
튀어나와 있어서, 그 높이의 복도에 동적 부품을 띄우기만 해도 센서에 걸친다.
보스판의 시소 지름길이 정확히 그것이었다. 버튼이 있는 판은 그 높이 복도를
부품 폭보다 좁게 두는 것으로 대응했고, 코어(`_buildButton`)는 건드리지
않았다.

뜻밖의 이득도 있었다. 보스판 20단계는 시소를 옮기면서 풍선이 저울 왼팔을 밀어
반대팔이 버튼을 누르게 됐다 — 설계 문서가 말하던 "부력 저울 피날레"가 이제
실제로 동작한다(전에는 풍선이 버튼을 직접 스치고 있었다). 열 판의 손 떨림
허용치는 하나도 나빠지지 않았고 다섯 판은 넓어졌다.

한계도 남겼다. 뒷마당 15단계처럼 **공이 트레이에 있고 버튼을 위에서 눌러야
하는 판**은, 정답 공이 지나가는 바로 그 지점이 언제나 놓을 수 있는 자리다
(배치 여유와 통과 폭의 차이가 2~4cm뿐). 출하 감사기의 격자는 비켜가지만
구조적으로 0은 못 만든다. 재질 함정을 유지하는 대가다.

최종 게이트는 100/100 스테이지 검증, 전수 지름길 감사 0건, `flutter analyze`
0건, 166개 테스트 통과다.

## 21차 — 정식 빌드를 폰에 올려 눈으로 확인하고, 다음 번호를 미리 만들다

20차까지의 수정이 전부 들어간 정식 빌드(1.0.0, 빌드 번호 2)를 A16에 설치해
직접 돌려 봤다. 확인한 것은 세 가지다.

**그림 자산은 한 장도 빠지지 않았다.** 저장소에 배경 6장·부품 17장·소리 7개·
스테이지 100판이 그대로 있고, 최근 한 달 이력에 지운 그림이 없으며, 만든
APK 안에도 같은 개수가 들어 있다. 릴리스 축소기가 리소스를 잘라내는 함정
(다른 앱에서 겪었다)이 여기서는 없다.

**실제 플레이가 된다.** 홈 → 뒷마당 2단계 → 트램펄린 배치 → 실행 → 클리어
(별 3개)까지 화면을 찍어 가며 확인했다. 새 힌트 분기("손잡이" 언급 없는 판)와
배경·부품·목표 그림이 모두 정상으로 보였다.

**지난 촬영의 흔적을 지웠다.** 14개 언어 스크린샷을 찍느라 앱 언어가 영어로
남아 있었다. 기기 설정(한국어)으로 되돌려 홈 화면이 "삐약과학 · 만들고 ·
실험하고 · 발견해요"로 뜨는 것을 확인했다.

그리고 빌드 번호를 **3**으로 올려 AAB를 미리 만들어 두었다. 1·2는 비공개
테스트 트랙에 올라간 번호라 콘솔이 재업로드를 거부하기 때문이다. 코드는
20차와 동일하고 번호만 다르다.

## 22차 — 광고를 한 자리에만 붙이다

수익화를 시작하기로 했다. 규칙은 하나로 정했다. **판을 만드는 동안에는
광고가 끼어들지 않는다.**

**배너를 버렸다.** 이 게임은 가로 화면 전체가 작업대다. 위쪽에는 목표
카드와 말풍선, 아래쪽에는 부품 트레이와 실행 버튼이 있고, 그 사이 전부가
부품을 끌어다 놓는 자리다. 어디에 띠를 붙여도 19~20차에서 고친 "공이
가려진다" 문제가 그대로 되살아나고, 손가락이 자주 지나는 자리라 오클릭도
난다. 홈 화면도 월드 카드가 화면을 꽉 채워서 사정이 같다.

**남은 자리는 판과 판 사이뿐이다.** 스테이지를 세 판 넘길 때마다, 다음
판으로 넘어가는 그 순간에 전면 광고를 한 번 띄운다. 받아 둔 광고가 없으면
아무 일도 없이 그냥 넘어간다 — 광고 때문에 다음 판이 늦게 열리는 일은
없다. 초기화·로드·표시 실패는 전부 `Ads` 안에서 삼킨다. 인터넷이 없으면
광고만 안 뜨고 100판은 평소대로 돌아간다.

**실수로 나갈 구멍을 먼저 막았다.** 디버그 빌드는 언제나 구글 테스트 ID를
쓰고, 정식 빌드는 실제 ID가 아직 자리표시자면 광고를 **아예 요청하지
않는다**. 테스트 광고가 이용자에게 보이거나 잘못된 ID로 요청이 가는 사고를
코드가 막는다.

**유럽 동의 창과 광고 등급.** 유럽·영국 이용자에게는 구글이 만든 동의 창을
앱 시작 때 띄운다(응답이 없으면 8초에서 끊어 시작을 막지 않는다). 그림체가
유아 친화적이라 광고 등급은 전체이용가(G)로 제한했다.

**띠 광고는 홈 화면 한 자리에만.** 월드 카드 아래 여백에 가로 기준 띠를
붙였다(세로 기준보다 낮아서 카드에서 뺏는 높이가 적다). 광고를 못 받으면
높이 0이 되어 홈 화면이 예전과 똑같다. 게임 화면은 여전히 비워 둔다 -
아래쪽 띠는 아이가 부품을 끌어내는 트레이와 힌트·홈 버튼이 붙어 있어
오클릭이 나는 자리다.

**신고 내용도 같이 고쳤다.** 광고 SDK가 읽는 값은 구글 기준으로 "수집·공유"다.
개인정보처리방침(한국어·영어)과 데이터 보안 표, 제출 체크리스트를 전부
광고가 있는 앱 기준으로 다시 썼다. 우리가 수집하는 것은 여전히 없지만,
그렇게 적으면 거짓이 된다. 애드몹에서 만들 것과 값을 넣을 자리는
[광고-붙이기.md](../store/광고-붙이기.md)에 따로 적어 두었다.

## 23차 — 메인 화면을 세우고, 게임 화면은 광고에 내주지 않기로 하다

**메인 화면.** 앱을 열면 월드 목록이 곧바로 떠서 "시작했다"는 느낌 없이
게임에 던져졌다. 아이콘·제목·큰 [시작하기] 하나짜리 화면을 앞에 세웠다.
들어가기 전에 언어를 고를 수 있도록 설정 버튼도 함께 둔다. 버튼 낱말은
14개 언어에 새 열쇠(`play`)로 넣었다 - 기존 `tutorialStart`("첫 실험 시작")는
두 번째부터 거짓말이 된다.

첫 화면이 바뀌면서 월드 목록은 더 이상 첫 route가 아니다. 마지막 판을
깬 뒤 `popUntil(isFirst)`로 돌아가면 메인 화면까지 튕겨 나가므로 `pop()`
한 번으로 바꿨다(판은 `pushReplacement`로 갈아끼우니 게임 route는 늘 하나다).
앱 전체를 띄우던 테스트 일곱 개는 시작 버튼을 한 번 누르고 들어가도록
공용 헬퍼(`test/ui/pump_app.dart`)를 거치게 했다.

**게임 화면 배너는 넣었다가 뺐다.** 판 위쪽에 띠를 얹고 판을 조금
줄여 봤다. 가려지는 것은 없었지만 판이 눈에 띄게 작아졌다. 띠를 낮춰
보려 했더니 구글이 주는 앵커 배너의 최소 높이가 50이라 더는 못 줄인다
(옛 32짜리는 이제 안 나온다). 좌우 빈 자리는 84뿐이라 광고 최소 너비
320에 한참 못 미친다. 결국 어느 자리에 넣어도 판이 12~14% 작아진다는
뜻이라, 게임 화면은 비워 두기로 했다. 띠는 메인 화면과 월드 목록 아래에만
둔다.

**초기화를 기다리지 않던 띠.** 홈 화면이 광고 SDK보다 먼저 뜨는 것이
보통이라, 위젯이 붙는 순간 "아직 준비 안 됨"으로 한 번 튕기고는 영영 다시
요청하지 않았다. 실기기에서 배너가 하나도 안 나와 알았다. `Ads.initialized`
future를 기다렸다가 요청하도록 고쳤다.

실기기에서 메인 화면과 두 배너가 나오는 것까지 확인했다. 전면 광고는
폰을 쓰는 중이라 눈으로 확인하지 못했다.
