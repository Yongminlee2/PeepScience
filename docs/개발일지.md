# 삐약과학 개발일지

시간 순서대로, 각 차수에서 만든 것과 **실제로 밟은 문제**를 남긴다.
같은 데를 다시 밟지 않기 위한 기록이므로 성공담보다 실패담이 자세하다.

## 1차 — 데이터 모델과 물리 코어

**첫 결정: 물리를 Flutter에서 완전히 떼어냈다.** `lib/sim/`은 Flutter를 import하지
않는 순수 Dart로 두고, 부품 조립·고정 타임스텝·목표 판정을 전부 여기 넣었다.
화면 없이 시뮬레이션을 돌릴 수 있어야 "전 스테이지 자동 검증"이 성립하기 때문이다.
(삐약푸쉬에서 `lib/engine/` 분리가 준 이득 — 솔버·검증 도구를 CLI로 돌린 것 — 을
그대로 계승한 구조다.)

**forge2d 0.15는 쓸 수 없었다.** 의존성을 추가하자 최신 0.15.0이 잡혔는데, 알고
보니 이 버전부터 순수 Dart 엔진을 버리고 **네이티브 Box2D v3 C 바인딩**으로
전환됐다(MSVC 필요, `dart run` 도구 불가). 순수 Dart 마지막 버전인 **0.14.2+1로
핀 고정**했다. 업그레이드하면 검증 파이프라인 전체가 무너지므로 이 핀은 의도된
것이다 — 캐럿(^) 없이 정확한 버전으로 박아 뒀다.

**좌표계는 처음부터 하나로 통일했다.** 미터 단위, **y 아래로 증가**, 원점 좌상단,
월드 16×9m, 중력 (0, 10). 화면 좌표와 방향이 같아서 렌더에서 축 뒤집기가 아예
없다. Box2D의 `setAsBox`가 **반폭·반높이(half-extents)** 를 받는 것만 주의하면
된다(부품 상수표는 전체 크기로 적혀 있어서 조립할 때 반으로 나눈다).

**시소가 무한 회전했다.** 중심 핀(revolute joint)만 달면 한쪽에 공이 얹힌 순간
계속 가속해 9.9라디안까지 돌며 공을 다 튕겨냈다. 실제 시소는 땅에 닿아 멈춘다는
점을 반영해 회전 제한(±0.6rad)을 걸었다. 이런 관절 상수도 부품 상수표(catalog)로
승격해 한 곳에서 튜닝한다.

**"통과하는 테스트"가 거짓말을 한 사건.** 풍선이 압정에 닿으면 터지는지 검사하는
테스트가 첫 판에 통과했는데, 뜯어 보니 풍선이 **화면 밖으로 떠올라 경계 정리에
지워진 것**을 "터졌다"로 오인한 것이었다. 마지막 y좌표가 압정 근처 범위(1.5~3.2m)
안이어야 통과하도록 조여서, "압정에서 펑"과 "화면 밖으로 실종"을 구분하게 했다.
이후로도 새 판정 로직마다 **일부러 조건을 뒤집어 테스트가 실제로 실패하는지**
확인하는 것을 규칙으로 삼았다.

## 2차 — 동력 부품: 톱니가 안 돌았다

톱니 전달의 첫 설계는 "마찰 전달"이었다 — 톱니를 마찰 높은 원으로 만들고 살짝
겹치게 놓으면 모터 톱니의 회전이 접촉면 마찰로 옆 톱니에 전달되리라는 것.
현실의 마찰차가 그렇게 돈다.

**결과: 0.0 rad/s. 얼마나 겹쳐도(0.03m든 0.2m든) 정확히 0이었다.** 원인은 튜닝이
아니라 물리였다. 마찰력의 상한은 `마찰계수 × 수직항력`인데, **둘 다 중심이 핀으로
고정된 원끼리는 서로를 누르는 힘이 생길 수 없다** — 겹침은 위치 보정으로만 처리되고
속도 수준의 수직 임펄스는 0에 머문다. 실제 마찰차가 도는 건 스프링이나 하중이
두 바퀴를 눌러주기 때문이고, 우리 장면엔 그런 게 없다.

그래서 **GearJoint로 전환**했다. 조립 시 톱니 가족(모터/일반/노)끼리 중심거리
≤ r1+r2+0.05면 맞물림으로 감지해 두 revolute 관절을 GearJoint로 묶는다. 외접
기어는 반대로 돌아야 하므로 비율 부호를 라이브러리 소스의 제약식에서 직접
유도했다(ratio = rB/rA). 결과는 정확히 반대 부호, 2.5/−2.5 rad/s로 잠긴다.
배치 시에는 근처 톱니에 중심거리 r1+r2−0.03으로 **스냅**시켜 감지 반경 안에
확실히 들어가게 했다.

**선풍기는 특수 케이스를 안 만들었다.** 바람 존 안의 모든 동적 물체에 같은 힘
1.5N을 준다. 고무공은 밀리고 쇠공은 거의 안 밀리는 건 질량 차이가 만들는 자연스러운
결과다(a = F/m). "부품 타입별 예외"를 코드에 넣기 시작하면 끝이 없다.

## 3차 — 렌더와 입력: 프레임워크의 함정 두 개

렌더는 고정 해상도 1600×900(레터박스), 1m = 100px. 그림 에셋이 아직 없으므로
모든 부품을 **물리 윤곽 그대로의 도형**으로 그린다 — 이 결정 덕에 "그림은 예쁜데
충돌이 어긋나 보이는" 문제를 원천 차단했고, 나중에 그림이 오면 파일만 넣으면
자동으로 교체되는 폴백 구조를 함께 만들었다.

**함정 1: 드래그 좌표가 두 배로 튀었다.** 프레임워크의 드래그 이벤트가 주는
"현재 위치(canvasEndPosition)"가 실제로는 `현재 + (현재 − 직전)`으로 계산돼
있어서, 손가락보다 이동량만큼 앞서 나갔다. 라이브러리 소스를 열어 확인한 실제
버그다. 시작 위치에 델타를 직접 누적하는 방식으로 우회했다.

**함정 2: 탭을 추가하니 드래그가 변했다.** 부품 선택(탭)을 게임에 붙이자 기존
트레이 드래그의 좌표 의미가 게임 전역에서 바뀌었다. 탭 인식기와 드래그 인식기가
**같은 제스처 아레나**에 들어가면서, 아레나 경합이 해소되는 첫 move 이벤트의
좌표 기준이 달라진 것. 이것도 근본 원인(인식기 등록 구조)을 소스로 확인하고,
두 경로 모두에서 수학적으로 같은 위치가 나오는 누적 방식으로 통일했다.

실기기(갤럭시 A16)에 올려 스크린샷으로 **도형 위치가 물리 좌표와 픽셀 단위로
일치**하는 것까지 확인하고 렌더 계층을 닫았다.

## 4차 — 편집 UX: 리뷰가 잡아낸 두 개의 조용한 버그

배치한 부품을 탭하면 선택 링 + 삭제 X + (회전 가능한 부품만) 회전 핸들이 뜬다.
회전은 5° 스냅. 트레이 남은 개수는 별도 카운터 없이 배치 목록에서 파생시켜
삭제 시 자동 복구되게 했다 — 상태가 두 곳이면 언젠가 어긋난다.

코드 리뷰에서 두 개가 걸렸다. 둘 다 조용히 잘못되는 종류였다.

1. **화면 맨 위에 놓은 부품은 삭제할 수 없었다.** 삭제 X가 부품 위 0.6m에 뜨는데,
   합법 배치 최상단(y=0.3)에서는 X의 히트 영역 전체가 화면 밖이었다. 버튼 위치를
   화면 안으로 클램프하는 함수 하나로 히트 판정과 렌더가 같은 좌표를 쓰게 고쳤다.
2. **삭제가 다른 부품의 각도를 오염시킬 수 있었다.** 회전 드래그 중(한 손가락)
   다른 손가락으로 그 부품을 삭제하면, 배치 목록 인덱스가 당겨지면서 회전 중이던
   인덱스가 **엉뚱한 부품**을 가리켰다. 삭제 함수 안에서 선택/회전 인덱스를 함께
   보정(같으면 해제, 크면 감소)하도록 한 곳에 모았다.

## 5차 — 화면 배선과 에디터

홈(월드 4 → 스테이지 10칸 그리드, 순차 해금) → 게임 → 클리어 시 다음 판으로,
마지막 판이면 홈으로. 설정에서 소리(저장만, 재생은 추후)와 언어(기기/한국어/영어).

**언어 전환이 조용히 안 먹혔다.** 루트에 리스너를 감아 전체를 리빌드시키려 했는데,
`const` 위젯은 정체성이 같아 프레임워크가 리빌드를 건너뛴다. 테스트가 먼저
실패해서 발견했고, 각 화면이 언어 상태를 직접 구독하는 구조로 바꿨다.

**엣지 투 엣지 대응.** 최신 안드로이드는 앱이 시스템 바 뒤까지 그리는 게 기본이라,
스크롤 목록에 시스템 바 여백을 더해주는 헬퍼를 만들어 마지막 항목이 내비게이션
바에 가리지 않게 했다(가족 앱에서 실제로 사용자가 겪었던 문제다).

**스테이지 에디터**는 디버그 빌드에서만 열린다. 모든 부품 무제한 + 지형·목표물
배치 + 목표 선택 + 같은 물리로 시험 실행 + **[솔루션 기록]**(현재 배치를 정답
데이터로 저장) + JSON 내보내기/가져오기. 40판을 좌표 숫자로 손으로 짜는 건
비현실적이라 콘텐츠 제작의 필수 도구다. 내보낸 JSON이 게임의 파서로 완전
왕복되는 것을 테스트로 못박았다.

**이 기계 특유의 함정도 하나.** 테스트를 기본 동시성으로 돌리면 다른 작업들과
메모리를 다투다 VM이 죽는다. `--concurrency=1`이면 안정적이다.

## 6차 — 첫 실기기 플레이테스트: 기계가 통과시킨 것을 사람이 떨어뜨렸다

40판·릴리스 빌드까지 끝내고 처음으로 폰에서 손가락으로 플레이한 날,
하루 만에 굵직한 결함이 다섯 개 나왔다. 전부 "테스트는 전부 통과"인 상태에서.

**실패했는데 아무 일도 안 일어나는 화면.** 부품 없이 ▶를 누르면 공이 1초 만에
화면 밖으로 사라지고, 게임은 실행 모드인 채 조용히 멈춰 보인다. 처음 하는
사람은 100% "고장"으로 읽는다. 목표 미달성 상태에서 움직일 물체가 다
사라지면 1.2초 뒤 자동으로 편집 모드로 돌아오게 했다.

**손가락 탭이 전부 죽어 있었다 — 이번 판 최대의 버그.** 부품 선택도, 회전도,
▶도 실제 손가락으로는 안 눌렸다. 원인: 탭 인식기와 드래그 인식기가 입력을
경쟁하는데, 포인터가 1픽셀이라도 움직이면 드래그 쪽이 가로챈다. 손가락은
반드시 몇 픽셀 흔들리므로 실기기에서 탭이 전멸 — 그런데 테스트와 개발용
기계 입력은 **이동량이 정확히 0**이라 전 과정에서 이 버그가 숨어 있었다.
탭 인식기를 아예 등록하지 않는 쪽으로 구조를 바꾸고(경쟁 자체를 소멸),
"15픽셀·0.3초 미만의 움직인 터치 = 탭"으로 드래그 스트림에서 탭을 합성했다.
이후 모든 입력 테스트는 **일부러 몇 픽셀 흔들리는 가짜 손가락**으로 짠다.
합성 입력 통과 ≠ 실터치 동작 — 이 저장소의 새 헌법이다.

**조작이 불편하다는 피드백 세 가지.** 놓은 부품을 고치려면 다시 탭해야 하고
(→ 놓자마자 자동 선택), 한 번 놓으면 옮길 수 없고(→ 잡아끌면 이동 — 두 번째
손가락이 이동을 가로채는 멀티터치 구멍은 리뷰가 잡아서 포인터 소유권으로
막았다), 회전 손잡이가 너무 작았다(→ 손잡이 확대 + 링 어디를 잡아도 회전.
이 과정에서 선풍기는 링이 자기 삭제 버튼을 항상 감싼다는 기하 문제가 나와
삭제 버튼 우선 가드를 넣었다).

**"3탄은 뭘 해야 할지 모르겠다."** 확인해 보니 버튼이 화면 밖 — 하단 트레이
바에 완전히 가려져 있었다. 전수 감사 결과 19판에서 24개 요소가 가려져 있었다.
물리 클리어(규칙 c)·배치 합법성(규칙 e)은 검증했지만 **"보이는가"는 검증한
적이 없었던 것.** 가시성 규칙(f)을 검증기에 추가하고 19판을 재조정했다.
검증 규칙은 이렇게 실패가 발견될 때마다 하나씩 늘어난다: 물리 → 배치 → 가시성.

**"깔끔한데 별로고, 저 네모 박스는 뭔지 모르겠다."** 배경·부품 그림은 예쁜데
UI 껍데기(트레이·버튼·목표 배지)가 무표정한 회색 박스라 서로 겉돌았다.
HUD 전체를 부품과 같은 스티커 재질(초콜릿 외곽선+캔디 색)로 다시 칠하고,
목표 배지는 깃발 달린 미션 카드로, 그리고 판에 들어설 때마다 **실제 목표물이
두 번 콩콩 커지는 연출**을 넣어 "저기에 넣는 거구나"가 말 없이 읽히게 했다.

이 라운드의 결론: 헤드리스 검증 파이프라인은 "풀 수 있는 게임"까지는
보장하지만, "사람 손에 쥐어줄 수 있는 게임"은 실기기에서 손가락으로
만져봐야 나온다. 둘 다 필요하다.

## 7차 — "물리는 되는데 왜 재미없지"를 다듬은 날

두 번째 플레이 감상은 뼈아팠다: "깔끔한 듯한데 조잡하고, 앵그리버드 같은
물리 손맛이 없다." 진단해 보니 물리 수치의 문제가 아니었다 — **물리가 잘
돌아간다는 사실이 눈에 안 보이는 것**이 문제였다.

**공이 구르는데 구르는 게 안 보였다.** 민무늬 원은 아무리 회전해도 정지 화면과
같다. 공 그림에 비대칭 무늬(고무공엔 흰 밴드, 쇠공엔 육각 볼트)를 넣는 것만으로
"데굴데굴"이 살아났다. 회전 각은 원래부터 물리와 동기화돼 있었다 — 보여줄
무늬가 없었을 뿐.

**부딪혀도 아무 일이 없었다.** 한 스텝에 속도가 크게 꺾이면(착지·충돌) 부품이
살짝 눌렸다 펴지고(스쿼시) 먼지가 퍽 나게 했다. 전부 뷰 계층에만 있는 연출이라
물리·검증은 1비트도 안 변한다. 앵그리버드 손맛의 8할은 이런 피드백이었다.

**부품들이 공중에 떠 보였다.** 지형이 무지 사각형이라 예쁜 배경 위에 붕 뜬
느낌 — 지형에 나무 판 질감을 입히고(그림이 오기 전엔 코드로 그림), 모든 부품
밑에 부드러운 그림자를 깔았다. 바닥이 생기니 비로소 "장소"가 됐다. 지형 타일
그림은 가로로 이어 붙는 심리스 조건이 핵심이라, 검수 때 좌우 끝 픽셀을 직접
비교해 이음새 차이 0을 확인하고 받았다.

홈 화면도 월드 카드에 배경 그림 썸네일과 진행 칩(n/10)을 달아 "고르는 맛"을
냈고, 스테이지 입장에 짧은 페이드를 넣었다.

이날의 교훈: 시뮬레이션의 정확함과 게임의 손맛은 다른 축이다. 정확함은
검증기가 지켜주지만, 손맛은 무늬 하나·먼지 한 줌·그림자 한 장이 만든다.

## 8차 — 출시 준비 완주

스토어 제출 패키지를 만들었다: 등록 문구(한/영 — 돈 이야기와 특정 상표를 쓰지
않는다는 집안 규칙을 지켰는지 기계로 재검사), 데이터 보안·콘텐츠 등급 설문

## 9차 — 상용화 UX·아트 폴리시

실기기에서 다시 보니 물리는 동작하지만 첫인상이 개발 빌드에 가까웠다. 홈은 기본
앱바와 설정 아이콘이었고, 트레이의 부품은 전부 같은 색 원으로 보였으며, 긴 판자를
선택하면 부품보다 훨씬 큰 점선 원이 떠 디버그 기즈모처럼 읽혔다. 클리어 화면도
`클리어!`와 아이콘 두 개뿐이라 과학 게임의 보상이 남지 않았다.

홈을 병아리 아이콘·태그라인·캔디 카드 상태가 있는 브랜드 셸로 다시 잡고, 게임에는
홈 버튼과 현재 월드·단계·목표·조작 안내를 넣었다. 트레이는 실제 부품 스프라이트를
비율에 맞춰 보여 주고, 직사각형 부품의 선택선은 실제 물리 윤곽을 따라가게 했다.
클리어는 큰 크림 카드 안에 재시도/다음 라벨과 목표별 과학 관찰 문장을 넣었다.

두 번째 실기기 검수에서는 UI가 아니라 부품 자체의 검은 면적이 문제였다. 14개
부품과 지형 타일을 새 아트 시스템으로 전면 교체했다: 검은 링 대신 슬림한 코코아색
선, 넓고 밝은 캔디 색면, 위쪽 밝은 면과 아래쪽 그늘 면의 소프트 셀 셰이딩. 공은
회전 밴드, 쇠공은 볼트, 기어류는 색과 동력 표식처럼 기능 판독 표시는 더 크게
남겼다. 지형 타일은 좌우 끝 픽셀 차이 0으로 다시 맞췄다.

실제 PNG가 늘면서 첫 프레임 이미지 디코딩이 트레이의 DragCallbacks 마운트를
잠깐 막는 테스트 레이스도 드러났다. 슬롯 입력은 즉시 마운트하고 그림만 비동기로
갈아 끼우게 바꿔 첫 터치가 이미지 로딩에 종속되지 않게 했다.

갤럭시 A16에서 홈 → 배치 → 80° 회전 → 물리 실행 → 바구니 클리어를 다시
완주했고 스토어 스크린샷 6장도 새 화면으로 교체했다. 최종 게이트는 `flutter
analyze` 0건, 전체 101개 테스트 통과, 릴리스 APK 빌드 성공이다.

## 10차 — 정답만 맞히던 판을 다시 하고 싶은 실험으로

아트와 조작은 많이 좋아졌지만 한 번 풀고 나면 다시 열 이유가 약했다. 이번에는
기존 40판을 버리지 않고 세 가지 재미 루프를 얹었다.

첫째, 대표 판 세 곳에 **연쇄 반응 리본**을 달았다. 공→도미노→목표처럼 현재
장치가 어떤 순서로 움직일지 실제 부품 그림과 점선으로 미리 보여 준다. 새 물리를
추가한 것이 아니라 이미 있던 인과관계를 읽히게 만든 변화다.

둘째, 뒷마당 5단계를 **예측하고 실험하는 판**으로 바꿨다. 고무공/쇠공 중 결과를
먼저 고르기 전에는 실행할 수 없고, 클리어 화면에서 예측과 결과가 같았는지 바로
돌려준다. 과학 설명을 결과 뒤에만 읽는 구조에서 가설→실험→관찰 구조로 한 단계
올라갔다.

셋째, 모든 클리어에 1~3성 숙련도를 저장한다. 기본 클리어 1성, 부품 수 제한이나
예측 성공 1성, 판 안의 민트 수집별 획득 1성이다. 별은 보너스 센서라 목표 달성을
막지 않으며, 기존 사용자의 `cleared_v1` 기록은 갑자기 0성처럼 보이지 않도록
3성으로 보존한다. 새 결과는 별점을 먼저 저장한 뒤 클리어 표식을 저장해 이 레거시
보정과 충돌하지 않게 했다.

민트 수집별은 투명 PNG 실에셋으로 만들었고, 월드 1·3의 10단계 정답 경로가 실제로
별 센서를 통과하면서도 클리어되는지 헤드리스 물리 테스트로 고정했다. 갤럭시 A16에서
예측 선택→쇠공 배치→실행→3성 결과, 연쇄 리본, 별 도전과 필드 수집별을 실터치로
검수했다. 결과 카드의 과학 문장과 버튼이 닿던 간격도 실기기 화면에서 발견해 수정했다.

최종 게이트는 `flutter analyze` 0건, 전체 113개 테스트 통과다.

## 11차 — 첫 판 앞에서 막히지 않는 실험 수첩

게임이 재미있어져도 첫 화면의 짧은 조작 문장 하나만으로는 어린 플레이어가
`목표 확인 → 부품 배치 → 회전 → 실행` 순서를 한 번에 이해하기 어려웠다. 첫
스테이지 첫 방문에만 자동으로 열리는 **삐약 박사의 실험 수첩**을 추가했다.

안내는 네 장이다. ① 현재 판에 맞는 실제 목표물 그림으로 미션을 보여 주고, ② 실제
판자와 손가락 아이콘으로 끌어놓기를 설명하고, ③ 기울어진 판자와 회전 아이콘으로
노란 손잡이를 알려 주고, ④ 실행 버튼과 수집별로 실험·재도전의 의미를 설명한다.
글만 넘기는 설명서가 아니라 기존 부품이 살짝 콩콩 움직이고 페이지가 미끄러져
바뀌는 작은 놀이처럼 만들었다.

완료·건너뛰기는 `tutorial_seen_v1`에 저장되어 다음 방문을 방해하지 않는다. 대신
모든 스테이지 우상단에 노란 전구 도움말 버튼을 두어 언제든 네 장을 다시 볼 수
있다. 안내를 닫으면 실제 목표물이 다시 펄스해 설명에서 플레이로 시선이 자연스럽게
이어진다. 한/영 문구와 48px 이상 버튼, 780×360 가로 화면 레이아웃을 테스트했다.

도움말의 첫 그림은 현재 목표에 맞춰 공→바구니, 쇠공→버튼, 풍선→압정,
공→도미노로 바뀌므로 다른 판에서 다시 열어도 잘못된 목표를 가르치지 않는다.

최종 자동 게이트는 `flutter analyze` 0건, 전체 116개 테스트 통과다.

## 12차 — 한 월드 20판, 총 80판으로 확장

네 월드를 각각 10판에서 20판으로 늘렸다. 11~20단계는 앞에서 배운 장치를
반대편으로 옮기거나 진행 방향을 뒤집어 다시 조립하는 **숙련 리믹스**다. 단순히
파일만 복제하지 않고, 모터 톱니처럼 회전 방향이 결과를 바꾸는 장치는 내부 구조를
유지한 채 무대 반대편으로 이동했다. 도미노·다단 장치는 연쇄 반응 표식을 더하고,
재료를 고르는 판에는 실행 전 예측, 모든 후반 판에는 정답 부품 수 기준 별 도전을
넣었다. 후반 판은 정답보다 여분 부품을 하나 더 줘서 처음에는 자유롭게 실험하고,
재도전에서는 더 간결한 장치로 줄일 수 있게 했다.

홈 카드에 20칸을 네 줄로 눌러 넣으면 짧은 가로형 휴대폰에서 터치 영역이 작아져서,
기존 5×2 버튼 크기를 유지한 `1–10 / 11–20` 페이지 전환기를 제목 줄에 넣었다.
진행 칩은 월드별 `n/20`과 누적 별 수를 계속 보여 준다.

새 40판은 원본 정답뿐 아니라 x±0.05m·각도±2° 손가락 오차 세 종류까지 모두
시뮬레이션했다. 첫 검수에서 반전된 3판이 탈락했고, 장치를 재배치하고 다시 돌려
최종 80/80판이 정답 클리어·오차 강건성·비자력 클리어·배치 합법성·가시성 검사를
전부 통과했다. 후반 판을 다시 만들 수 있는 생성 규칙은
`tool/generate_expert_stages.dart`에 남겼다(다음 차수에서 복합 장치 생성기로 확장).

릴리스 APK를 갤럭시 A16에 기존 기록을 유지한 채 설치했다. 홈에서 기존 클리어가
`10/20`으로 보이고, `11–20` 페이지의 11단계만 정상 해금되는 것을 확인했다.
11단계는 실제 손가락 드래그·80° 회전·실행으로 클리어해 최소 부품 도전 3성까지
저장했다.

최종 자동 게이트는 `flutter analyze` 0건, 전체 121개 테스트 통과다.

## 13차 — 반전 리믹스를 숙련자용 복합 장치 40판으로 교체

처음 만든 11~20단계는 방향 전환과 여분 부품 도전은 있었지만, 40판 중 32판의
정답이 부품 하나라서 "여러 기믹을 조립하는 숙련자 구간"이라고 부르기 부족했다.
오너 피드백 뒤 후반 40개 JSON을 전부 다시 설계했다.

아이 방은 시작 공까지 직접 싣고 판자 경사·다리·도미노 릴레이를 완성한다. 뒷마당은
시소+쇠공, 2연속 트램펄린, 시소+쇠공+트램펄린, 다중 풍선+압정을 섞었다. 공장은
완성돼 있던 모터를 트레이로 내리고 모터+일반 톱니+패들 전달계를 직접 맞물리게
했으며, 트램펄린이나 압정까지 이어진다. 우주는 선풍기+공, 선풍기+시소+공,
모터+패들+선풍기, 모터+패들+트램펄린, 두 선풍기로 떨어진 도미노 두 무리를 각각
쓰러뜨리는 판, 판자+선풍기+톱니+압정 종합 장치로 구성했다.

후반 40판은 전부 정답 부품 2개 이상, 35판은 서로 다른 부품 종류 2개 이상,
12판은 3~4개 부품을 쓴다. 플레이어 정답에는 판자·두 공·시소·모터/일반/패들
톱니·선풍기·트램펄린·압정까지 10종이 실제로 등장한다. 더 중요한 새 게이트는
**정답 부품 하나씩 제거하기**다. 40판의 모든 정답에서 각 부품을 하나씩 빼고
물리를 다시 돌려 모두 실패하는지 검사해, 클리어에 필요 없는 장식용 도구가 하나도
남지 않게 했다.

생성기는 `tool/generate_expert_stages.dart`로 이름을 바로잡았다. 80판 전체가 원본
정답과 x±0.05m·각도±2° 오차 세 종류, 배치 합법성, 비자력 클리어 검사를 다시
통과했다.

최종 자동 게이트는 `flutter analyze` 0건, 전체 122개 테스트 통과다.

갤럭시 A16에서는 검수용 전체 해금 릴리스로 w3_s12를 열어 모터→일반 톱니→패들
세 부품을 직접 드래그·스냅하고 3성 클리어했다. 검수 뒤에는 전체 해금 옵션이 없는
일반 릴리스를 다시 빌드·설치해 순차 해금 상태로 돌려놓았다.

## 14차 — 부품 개수가 아니라 우회 불가능성으로 숙련판 재설계

13차 결과는 부품 수는 늘었지만 핵심 난이도 검수가 틀렸다. 바구니 목표에서 공을
트레이에 함께 넣어 둔 판은 장치를 만들 필요 없이 공을 바구니 위에 놓으면 끝났다.
"정답 부품 하나씩 제거" 검사도 기록된 정답만 확인했을 뿐, 전혀 다른 한 부품
우회 해법은 찾지 못했다.

후반 40판의 저작 원칙을 다시 세웠다. 바구니·버튼·도미노 목표에서는 공을 트레이에
주지 않고 시작점 프리셋에 고정한다. 풍선 목표에서는 압정을 프리셋에 고정해 풍선이
그곳까지 이동하도록 한다. 월드 1은 시작 공 뒤에 2~3개의 끊어진 교량과 발사 경사를
조립하는 장거리 코스, 월드 2는 고정 쇠공이 시소를 때린 뒤 두 트램펄린을 연속으로
타는 코스와 양쪽 상승 풍선을 각각 판자 두 장으로 유도하는 코스, 월드 3은 모터부터
패들까지 4~5개의 톱니를 직접 맞물리는 코스, 월드 4는 팬+판자, 팬+시소+트램펄린,
모터+패들+팬, 양쪽 풍선용 판자+팬+톱니 장치로 교체했다.

새 `tool/audit_expert_shortcuts.dart`는 각 숙련판의 트레이 부품 하나를 목표물·시작
물체 주변과 화면 전체 대표 좌표, 회전 가능한 여러 각도에 실제로 놓고 700스텝씩
시뮬레이션한다. 첫 실행에서 트램펄린 하나, 판자 하나, 팬 하나로 끝나는 우회 6판을
찾아 모두 불합격 처리했다. 해당 판을 3단 장치 또는 좌우 두 목표 장치로 바꾼 뒤
재실행한 결과 샘플 단일 부품 우회는 0건이다.

최종 후반 40판은 전부 목표 직행 부품 지급 금지, 37판이 정답 3개 이상, 26판이
서로 다른 도구 2종 이상이다. 기존의 정답 부품 하나씩 제거 검사도 계속 유지하고,
80판 원본 정답·x±0.05m 지터·회전 가능한 판자/선풍기 각도±2°·비자력·배치
합법성 검사를 다시 통과했다.

A16에서 새 시소 코스를 직접 배치하려던 중 트램펄린 solution에 -4°가 적힌 문제도
발견했다. 게임은 트램펄린·시소·톱니를 회전시킬 수 없으므로 자동 시뮬레이션만
통과하고 사람은 만들 수 없는 정답이었다. 회전 불가 부품의 정답 각도를 0°로
강제하는 검증을 추가하고, 해당 뒷마당 8판·공장/우주 관련 판과 기존 w2_s06까지
전부 0° 배치만으로 다시 튜닝했다. 지터도 실제 회전 가능한 판자·선풍기에만 각도
오차를 적용한다.

최종 자동 게이트는 80/80 스테이지 검증, 샘플 단일 부품 우회 0건,
`flutter analyze` 0건, 전체 124개 테스트 통과다. 일반 릴리스 APK를 A16에
재설치하고 w2_s11에서 트레이의 시소와 트램펄린 두 개를 실제 손가락 드래그로
0° 배치한 뒤 `시소→1차 반동→2차 반동→바구니` 3성 클리어까지 확인했다.
